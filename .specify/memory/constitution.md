## Core Principles

### I. 제품 방향과 문서 기준
모든 작업은 `IDEA.md`를 최신 제품 방향과 범위의 최우선 기준으로 사용해야 한다(MUST).
작업자는 `IDEA.md` → `API_SPEC.md` → 해당 `agent_specs` → `specs` 순서로 문서를 읽고,
`API_SPEC.md`를 클라이언트와 서버 사이의 공개 요청·응답 계약 기준으로 사용해야 한다(MUST).
이전 `Docs` 제안·PRD·Skill 참고 문서는 맥락 자료로만 사용할 수 있으며(MAY),
`IDEA.md`·`API_SPEC.md`와 충돌하는 제안은 구현하지 않는다(MUST NOT).
이 원칙은 서로 다른 작업자가 오래된 제안이나 서로 다른 계약을 기준으로 개발하는 일을 막는다.

### II. MCP 제공 형태와 실행 경계
서비스는 MCP로 제공한다(MUST). MCP는 별도 제품 개발 전 임시 포장이나 시연 전용 수단이 아니다(MUST NOT).
독립 사용자 클라이언트를 개발하거나 스토어·설치 파일 형태로 제공하지 않는다(MUST NOT).
Hermes + Upstage Solar Pro4를 개발과 시연에 사용한다(MUST).
MCP 서버(본인의 도구 계층)와 내부 FastAPI 백엔드(친구의 계산 계층)는 서로 다른 실행 경계이며(MUST),
두 경계를 혼동하거나 로컬 stdio로 원격 백엔드를 제공한다고 설명하지 않는다(MUST NOT).
우선 연결 방식은 Hermes가 로컬 MCP 서버를 실행하는 stdio이며(MUST),
원격 MCP·접근 제어·제출 요구 사항은 별도 확인이 필요하다(MAY).

### III. 검증 가능한 코드와 실제 데이터
경로 유효성, 시간 계산, 상태 전이, 횟수 제한, 권한 검증은 테스트 가능한 코드로 처리한다(MUST).
AI(Solar Pro4 및 백엔드 Agent 런타임)는 자연어 입력 구조화, 필요한 확인 질문, 검증된 계산 결과의 설명에만 사용한다(MUST).
실시간 교통편, 막차시각, 경로, 요금, 이동시간을 생성하거나 추측하지 않는다(MUST NOT).
모든 교통 결과는 실제로 확인한 데이터의 출처와 기준시각을 포함해야 한다(MUST).
Demo·fixture 데이터는 실제 데이터와 명확히 표시·분리해야 하며(MUST),
운영 조회 실패를 Demo 결과로 자동 대체하지 않는다(MUST NOT).
실행하지 않은 테스트·조회·저장·배포를 성공으로 보고하지 않는다(MUST NOT).

### IV. 사용자 확인과 계획 통제
경로 계산 전에는 해석된 장소·시각·도착 여유·이동수단을 사용자에게 표시하고 명시적 확인을 받는다(MUST).
넓은 지역명·학교명·“집” 같은 표현을 임의의 장소로 확정하지 않는다(MUST NOT).
이미 확정된 명확한 조건을 불필요하게 다시 질문하지 않는다(MUST NOT).
`ready_for_plan=true`는 입력 준비 완료이지 사용자 동의가 아니다(MUST).
모델이 `user_confirmed=true`를 생성했다는 사실만으로 사람의 확인을 검증했다고 간주하지 않는다(MUST NOT).
재탐색은 MVP에서 사용자 요청으로 시작하며(MUST), 새 결과는 사용자가 선택하기 전까지 기존 계획에 적용하지 않는다(MUST NOT).
재탐색 실패·취소는 기존 기록을 삭제하지 않으며(MUST NOT), 이전 경로가 여전히 유효하다는 보장으로 표시하지도 않는다(MUST NOT).

### V. 계약 우선 통합과 실행 구조
두 개발자는 Spec Kit을 사용해 명세·계획·작업을 관리한다(MUST).
공개 API의 경로·필드·상태·오류 의미를 변경하려면 두 개발자가 먼저 합의하고
`API_SPEC.md`와 `Docs/api/examples.json`을 함께 갱신한 뒤 구현한다(MUST).
클라이언트와 서버는 동일한 구조화 JSON 계약을 사용하며(MUST),
제공처 교체는 공개 계약을 보존하는 Adapter로 격리한다(MUST).

서비스의 MainAgent는 요청과 현재 상태를 바탕으로 SubAgent의 실행 순서와 결과 취합을 지휘한다(MUST).
한 SubAgent는 역할에 필요한 여러 Skill을 사용할 수 있고(MAY),
매 요청에 모든 Skill을 실행하지 않는다(MUST NOT).
이 서비스 실행 구조를 개발용 코딩 에이전트 분업과 혼동하지 않는다(MUST NOT).
`.hermes/skills`를 Skill 원본의 단일 저장 위치로 사용한다(MUST).
원본이 없는 준비 폴더에 가짜 `SKILL.md`를 만들어 구현 완료를 표현하지 않는다(MUST NOT).

### VI. MVP 범위, 보안, 증거 기반 완료
작업은 2명·4일 MVP 범위 안에서 수행한다(MUST).
택시비 상한선·택시 최적화·상시 GPS 추적·자동 재탐색·Calendar 자동 동기화·백그라운드 알림 등
보류 기능을 승인 없이 MVP에 포함하지 않는다(MUST NOT).
UserData DB·회원가입·영구 이동 이력·출발/도착 상태 버튼은 현재 MCP 필수 범위가 아니다(MUST NOT).
이를 추가할 때는 저장 항목·사용자 식별·인증·접근 제어·삭제 정책과 API 계약을 구현 전에 합의한다(MUST).

교통·백엔드 AI·DB 자격증명은 백엔드 실행 환경에서 관리하고(MUST),
Hermes 모델 자격증명은 Hermes 실행 환경의 비밀 설정으로 관리한다(MUST).
실제 키·비밀 값을 저장소·설정 예제·도구 응답·로그·시연 영상에 포함하지 않는다(MUST NOT).
접근 제어·호출 제한은 공개 백엔드에서 별도로 검토한다(MUST).

완료 주장은 재현 가능한 실행 증거에 근거해야 한다(MUST).
설치·실행·Hermes 연결·백엔드 배포 방법, 필수 설정, 지원 범위, 알려진 제한을 문서화한다(MUST).

## 기술 및 운영 제약

- 대상 지역은 서울이며, 실제 지원 범위는 검증된 교통 데이터의 지역·노선·운행일로 제한한다(MUST).
- 백엔드는 FastAPI, 패키징은 Docker, 배포 대상은 GCP Cloud Run을 기준으로 한다(MUST).
  Cloud Run 컨테이너는 플랫폼의 `PORT` 환경변수와 `0.0.0.0`을 사용해야 한다(MUST).
- 시간대는 `Asia/Seoul`만 허용한다(MUST). 날짜와 시간대를 함께 처리하고 자정 이후 도착과 운행일을 구분한다(MUST).
- 목표 도착시각 = 약속의 도착 Deadline − 사용자의 도착 여유시간(MUST).
  Buffer 시간은 leg·total_duration_minutes에 이미 반영되어 있으며(MUST),
  연동 계층이나 표시 단계에서 다시 더하거나 출발시각에서 다시 빼지 않는다(MUST NOT).
- MCP 도구와 백엔드 API의 연결은 아래 표처럼 관리한다(MUST).
  - `get_capabilities` ↔ `GET /api/v1/capabilities`
  - `search_places` ↔ `GET /api/v1/places`
  - `interpret_trip` ↔ `POST /api/v1/mobility/interpret`
  - `plan_journey` ↔ `POST /api/v1/journeys/plan`
  - `replan_journey` ↔ `POST /api/v1/journeys/replan`
- `health`는 내부 연결 확인용이며(MUST), 정확한 경로·필드·상태·오류 의미는 `API_SPEC.md`를 따른다(MUST).
- 원격 백엔드 연결에는 HTTPS를 사용한다(MUST). 로컬 개발 HTTP는 별도 구분한다.
  MCP 클라이언트가 DB에 직접 접속하지 않는다(MUST NOT).
- Mock과 실제 서버는 같은 공개 JSON 구조를 사용해야 하며(MUST),
  Mock 날짜·서버 시각을 실제 운행 계산에 주입하지 않는다(MUST NOT).

## 개발 워크플로와 품질 게이트

1. 작업을 시작하기 전에 기준 문서와 기존 구현을 읽고, 확정 사항과 미확정 사항을 구분한다(MUST).
2. API 또는 사용자 데이터 계약 변경은 구현보다 먼저 합의·문서화하고 fixture와 함께 갱신한다(MUST).
3. 가장 작은 약속 이동 흐름인 자연어 입력 → 조건 확인 → 실제 데이터 조회 → 권장 출발시각·근거 표시를
   먼저 종단 간 연결한다(MUST). 막차와 재탐색은 검증된 지원 범위 안에서 확장한다(MUST).
4. 시간대·자정 경계·도착 여유·Buffer 중복 계산·상태 전이·사용자 고정 조건·
   데이터 없음과 제공처 장애의 구분을 자동화된 테스트 또는 재현 가능한 통합 검증으로 확인한다(MUST).
5. MCP 계층과 백엔드는 개발 중 정기적으로 통합하며(MUST),
   최종일 전에 다른 환경에서 Hermes의 도구 발견·호출과 백엔드 응답 수신을 검증한다(MUST).
   배포 서버 연결 상태도 별도로 기록한다(MUST).
6. 검토자는 구현이 본 헌법·`IDEA.md`·`API_SPEC.md`·관련 spec과 일치하는지 확인하고,
   실행한 검증과 실행하지 못한 검증을 결과에 구분해 기록한다(MUST).
7. README.md의 “두 사람의 분업” 섹션은 작성자(친구) 관점에서 역할이 반대로 적혀 있으므로,
   실제 분업은 이 헌법과 `IDEA.md`·`BACKEND_HANDOFF.md`를 기준으로 한다(MUST).

## Governance

이 헌법은 Project Jigeum의 공통 개발 원칙을 성문화한다.
제품 범위는 `IDEA.md`, 공개 API 계약은 `API_SPEC.md`, 작업 수행 규칙은 루트 `AGENTS.md`가
각각의 권위 있는 상세 기준이며, 이 헌법은 이들과 일관되게 해석한다(MUST).
충돌이 발견되면 구현을 중단하고(MUST), 권위 있는 문서를 먼저 합의·수정한 뒤 헌법의 동기화 필요성을 검토한다(MUST).

헌법 개정은 변경 이유, 영향을 받는 원칙과 산출물, 필요한 마이그레이션 또는 재검증을 기록해야 한다(MUST).
API·저장·인증·권한·지원 범위에 영향을 주는 개정은 두 개발자의 합의가 필요하다(MUST).
모든 spec·plan·tasks와 코드 리뷰는 구현 시작 전과 완료 주장 전에 헌법 준수를 확인해야 한다(MUST).
예외는 범위와 만료 조건을 문서화한 명시적 승인 없이는 허용되지 않는다(MUST NOT).

버전은 Semantic Versioning을 따른다(MUST).
원칙 제거 또는 호환되지 않는 재정의는 MAJOR,
원칙·섹션 추가나 실질적 확장은 MINOR,
의미를 바꾸지 않는 설명·표현 수정은 PATCH로 증가시킨다(MUST).
최초 채택일은 유지하고, 실제 변경이 있을 때 마지막 개정일을 갱신한다(MUST).
