**Feature Branch**: `feature/mcp-server-integrate` (현재 작업 브랜치, 새 브랜치 생성 없음)
**Created**: 2026-09-16

**Input**: User description: "지금 세션에서는 네이버 길찾기 API 연동만 진행하겠습니다. 사용자는 NCP로부터 API키를 발급 받은 상태입니다. 연동을 위한 spec부터 수립합시다. 모호하거나 사용자 정보 제공이 필요한 사안은 질의를 해주십시오."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 확인된 장소 사이의 실제 자동차 경로 조회 (Priority: P1)

서비스 담당자는 확인된 출발지·목적지를 이용해 네이버가 제공하는 실제 자동차 경로의 소요 시간과 거리를 조회하고, 조회 결과의 출처와 기준시각을 확인한다. 장소를 임의로 선택하거나 자동차 경로를 대중교통 경로로 설명하지 않는다.

**Why this priority**: 현재 경로 제공자는 Mock 데이터에 의존한다. 이번 기능의 최소 가치는 검증 가능한 실제 자동차 경로를 확보하는 것이다.

**Independent Test**: 확인된 좌표와 준비된 인증 설정으로 자동차 경로 하나를 조회하고, 제공처 결과의 소요 시간·거리와 반환값 및 출처 표시를 비교한다. 실제 조회와 고정 응답 검증을 구분한다.

**Acceptance Scenarios**:

1. **Given** 출발지·목적지 좌표가 확인되었고 사용할 네이버 서비스가 활성화되어 있을 때, **When** 담당자가 자동차 경로 조회를 요청하면, **Then** 제공처에서 성공으로 반환한 경로의 소요 시간·거리·출처·조회 기준시각을 확인할 수 있다.
2. **Given** 조회 결과가 자동차 도로 경로일 때, **When** 결과를 전달하면, **Then** 이를 버스·지하철·도보·자전거 또는 막차 경로로 표시하지 않는다.
3. **Given** 제공처가 조회 시점의 실시간 교통 상황을 반영할 때, **When** 결과를 확인하면, **Then** 현재 교통 상황에 따른 추정치임을 알 수 있고 특정 미래 출발시각의 이동시간이 검증되었다는 설명을 받지 않는다.
4. **Given** 출발지·목적지가 미확정이거나 좌표를 확보하지 못했을 때, **When** 조회를 요청하면, **Then** 임의의 좌표로 조회하지 않고 확인이 필요한 입력을 식별한다.

### User Story 2 - 조회 실패와 미지원 범위의 정확한 구분 (Priority: P1)

서비스 담당자는 입력 오류, 경로 없음, 지원하지 않는 이동수단, 인증·사용 권한 문제, 사용량 제한 및 일시적인 제공처 장애를 구분한다. 실제 조회가 실패한 상황에서는 성공한 것처럼 보이는 가상 경로를 받지 않는다.

**Why this priority**: 실제 정보와 가상 정보를 혼동하면 사용자가 잘못된 출발 판단을 할 수 있다.

**Independent Test**: 각 실패 유형의 고정 응답과 통신 실패를 재현해 결과가 실패로 유지되는지 확인한다. 실제 인증 정보 없이도 검증을 수행할 수 있어야 한다.

**Acceptance Scenarios**:

1. **Given** 인증 정보가 누락되거나 사용할 서비스가 미설정일 때, **When** 연동을 시작하면, **Then** 설정 문제를 식별하고 불완전한 인증 정보로 조회하지 않는다.
2. **Given** 인증·권한 오류, 사용량 제한 또는 제공처 장애가 발생했을 때, **When** 조회 결과를 반환하면, **Then** 실패 종류를 전달하고 Mock 경로를 실제 조회 결과로 대체하지 않는다.
3. **Given** 통신은 성공했지만 제공처가 길찾기 실패를 반환하거나 경로가 없을 때, **When** 결과를 판정하면, **Then** 유효한 경로 조회 성공으로 처리하지 않는다.
4. **Given** 버스·지하철·도보·자전거·막차 조회를 요청했을 때, **When** 네이버 자동차 길찾기를 사용할 수 있는지 판단하면, **Then** 해당 범위를 미지원으로 구분하고 자동차 소요 시간을 대신 반환하지 않는다.
5. **Given** 기존에 선택한 이동 계획이 있을 때, **When** 네이버 조회가 실패하면, **Then** 이 조회 때문에 기존 계획을 삭제하거나 자동 변경하지 않는다.

### User Story 3 - 기존 기능을 보존하는 연동 검증 (Priority: P2)

서비스 담당자는 네이버 연동과 기존 Mock 검증을 구분해 실행하고 어떤 결과가 실제 조회에서 나온 것인지 확인한다. 이번 작업으로 기존 대중교통 계약이나 Hermes 사용 흐름이 임의로 바뀌지 않는다.

**Why this priority**: 제공처 연동의 성공 여부와 서비스 전체의 구현 완료 여부를 분리해야 기존 기능과 병행 개발을 보존할 수 있다.

**Independent Test**: 네이버 조회 검증과 기존 Mock 검증을 각각 실행하고 실제 조회 성공 여부·실행한 검증·미검증 항목이 별도로 기록되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 네이버 인증 정보가 없는 검증 환경일 때, **When** 고정 응답 검증을 실행하면, **Then** 유료 외부 호출 없이 정상·실패 응답 처리를 검증하고 이를 실제 조회 성공으로 보고하지 않는다.
2. **Given** 실제 네이버 조회를 실행했을 때, **When** 검증 결과를 보고하면, **Then** 요청한 경로, 성공 또는 실패 여부, 출처와 조회시각을 비밀값 없이 확인할 수 있다.
3. **Given** 기존 대중교통·Mock 기능을 검증할 때, **When** 네이버 연동 작업을 적용하면, **Then** 합의되지 않은 공개 계약 변경이나 실제 조회 실패 시 자동 Demo 전환이 추가되지 않는다.

### Edge Cases

- 출발지·목적지 좌표 누락, 위도·경도 순서 혼동, 범위를 벗어난 좌표 및 숫자가 아닌 값.
- 출발지와 목적지가 같거나 너무 가까워 제공처가 경로를 반환하지 못하는 경우.
- 유효한 좌표이지만 자동차 경로를 제공할 수 없는 지역 또는 도로인 경우.
- 인증 정보는 발급되었지만 Directions가 활성화되지 않았거나 발급 서비스와 요청 대상이 다른 경우.
- 통신 성공과 길찾기 성공 여부가 서로 다른 응답, 빈 경로, 소요 시간·거리 누락 또는 잘못된 자료형.
- 소요 시간이 1분 미만이거나 분 단위로 나누어떨어지지 않는 경우.
- 동일한 입력으로 다시 조회했지만 실시간 교통 상황 때문에 경로나 이동시간이 달라지는 경우.
- 응답 지연·연결 실패·사용량 제한·제공처 서버 오류.
- 조회가 자정 전후에 이루어져 현지 날짜와 시각이 바뀌는 경우.
- 제공처의 일부 시각 필드에 시간대 또는 의미가 명확하지 않은 경우. 의미 확인 없이 도착시각으로 사용하지 않는다.
- 고정 응답과 실제 조회 결과가 섞이는 경우.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 NCP Maps Directions 15에서 지원하는 자동차 길찾기만 조회해야 한다. 발급된 인증 정보가 있다는 사실만으로 실제 조회 성공이 확인되었다고 간주하지 않는다.
- **FR-002**: 이번 기능의 적용 범위는 사용자 응답으로 확정해야 한다. [NEEDS CLARIFICATION: 네이버 Directions 15의 자동차 경로 제공자 연동·독립 검증을 진행하는가, 자동차 약속 출발 계산·재탐색까지 포함하는가, 아니면 대중교통이 목적이므로 네이버 연동을 보류하는가?]
- **FR-003**: 실제 조회 대상은 사용자에게 확인된 출발지·목적지여야 한다. 서비스 사용 흐름에서 계산을 시작하기 전 조건 확인을 유지하고, 단독 연동 검증에서는 담당자가 명시적으로 제공한 검증 입력을 사용한다.
- **FR-004**: 시스템은 담당자 또는 사용자가 명시적으로 제공하고 확인한 출발지·목적지의 위도·경도를 조회 입력으로 사용해야 한다. 이번 기능에 장소 검색·주소 검색·Geocoding·장소 ID를 좌표로 바꾸는 신규 기능을 포함하지 않는다.
- **FR-005**: 시스템은 조회에 필요한 좌표의 존재 여부, 숫자 여부 및 위도·경도 범위를 검증해야 하며, 좌표가 없는 장소 ID를 임의 좌표로 변환하지 않아야 한다.
- **FR-006**: 시스템은 성공한 경로에서 출발지·목적지, 자동차 이동수단, 전체 소요 시간, 전체 거리, 경로 선택 기준, 제공처 이름, 조회 기준시각 및 실제·Demo 구분을 식별할 수 있어야 한다. 필요한 정보가 없는 응답은 정상 경로로 사용하지 않는다.
- **FR-007**: 시스템은 제공처의 소요 시간·거리 단위를 정확하게 해석해야 한다. 소요 시간을 정수 분으로 표현하는 경우 올림하여 원본보다 짧게 표시하지 않으며, 원본값에 없는 거리·시간을 추측하지 않는다.
- **FR-008**: 시스템은 조회 시점의 자동차 이동시간을 미래 출발시각의 예측, 대중교통 시간표, 도보 시간, 택시 배차·탑승 대기시간 또는 막차 정보로 간주하지 않아야 한다.
- **FR-009**: 시스템은 통신 결과와 제공처의 길찾기 성공 여부를 각각 확인해야 한다. 경로 없음, 미지원, 입력 오류, 인증·권한 문제, 사용량 제한, 제공처 장애 및 유효하지 않은 응답을 구분해야 한다.
- **FR-010**: 시스템은 실제 조회 실패를 Mock 또는 모델이 생성한 경로로 대체하지 않아야 한다. 기존 계획을 자동 변경하지 않으며, 재탐색이 포함되면 새 후보를 적용하기 전에 사용자 선택을 받아야 한다.
- **FR-011**: 시스템은 실제 조회 결과에 데이터 출처와 조회 기준시각을 포함하고 서비스 시각을 `Asia/Seoul`로 처리해야 한다. 시간대가 불명확한 제공처 시각을 확인 없이 도착시각이나 운행일로 변환하지 않는다.
- **FR-012**: 인증 정보는 서버의 비밀 설정으로만 제공받고, 요청 결과·오류·로그·문서·테스트 자료·저장소에 실제 비밀값을 포함하지 않아야 한다. 명세 작성 과정에서는 키 값 제공을 요구하지 않는다.
- **FR-013**: 시스템은 사용자가 확인한 `Application Services > Maps`의 `Directions 15`를 연동 대상으로 사용해야 한다. 서비스가 다르거나 필요한 인증 설정이 준비되지 않은 환경에서는 다른 상품으로 자동 전환하지 않고 설정 문제를 반환한다.
- **FR-014**: 실제 외부 조회는 담당자가 정한 제한된 검증 입력으로 수동 실행해야 한다. 기본 검증은 외부 호출 없이 수행하며 자동 반복 조회·상시 감시·배포를 추가하지 않는다. 실제 호출 횟수와 비용 범위는 구현 계획에서 실행 전에 확정한다.
- **FR-015**: 기존 대중교통·Mock 동작과 공개 계약을 보존해야 한다. 자동차 이동수단 또는 좌표 입력 등 공개 계약을 변경해야 하는 범위를 선택하면 공동 합의와 `API_SPEC.md`·`Docs/api/examples.json`의 동시 갱신을 구현 선행 조건으로 둔다.
- **FR-016**: 시스템은 정상 조회와 각 실패 유형을 인증 정보 없이 검증할 수 있어야 한다. 고정 응답 검증, 실제 네이버 조회, 기존 서비스 검증 및 아직 수행하지 않은 통합 검증을 구분해 보고한다.

### Key Entities *(include if feature involves data)*

- **확인된 조회 조건**: 직접 제공한 출발지·목적지의 위도·경도, 각 장소의 확정 여부 및 자동차 경로 조회 목적.
- **자동차 경로 결과**: 제공처가 반환한 경로 선택 기준, 소요 시간, 거리, 이동수단 및 검증된 출발·도착 지점.
- **데이터 출처**: 제공처 이름, 조회 기준시각, 실시간 또는 Demo 여부. 미래 경로·운행일 검증과는 구분한다.
- **조회 실패**: 실패 유형, 비밀정보가 제거된 원인 설명 및 성공 경로로 사용할 수 없는 상태.
- **연동 설정**: 활성화한 서비스·Directions 종류와 인증 설정의 준비 상태. 실제 비밀값은 이 명세의 기록 대상이 아니다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 승인된 실제 검증 입력 최소 1건에서 실제 자동차 경로 조회에 성공하고 소요 시간·거리·출처·조회 기준시각을 모두 확인할 수 있다. 실제 호출 전에는 이 기준을 미검증으로 보고한다.
- **SC-002**: 정상 응답과 시간 단위 경계값을 포함한 고정 검증 사례에서 반환한 거리 및 정규화된 소요 시간이 기대값과 100% 일치한다.
- **SC-003**: 좌표 누락·잘못된 좌표·미지원 이동수단·경로 없음·인증 또는 권한 문제·사용량 제한·통신 실패·잘못된 응답의 검증 사례 모두에서 실패가 식별되고, 성공한 실제 경로 또는 Mock 대체 결과로 보고되는 사례가 0건이다.
- **SC-004**: 실제 결과를 미래 교통 예측·대중교통·도보·막차 정보로 오인할 수 있는 검증 사례가 0건이며, 실제 조회와 Demo 결과의 출처를 모든 검증 사례에서 구분할 수 있다.
- **SC-005**: 새 문서·검증 산출물·조회 결과·오류 및 로그에 실제 인증 비밀값이 포함되는 사례가 0건이다.
- **SC-006**: 이번 연동 때문에 기존 기능의 적용 대상 검증이 새로 실패하는 사례와 합의 없는 공개 계약 변경이 각각 0건이다. 기존 실패가 있다면 연동으로 발생한 실패와 분리해 기록한다.

## Assumptions

- 사용자는 NCP 인증 정보를 발급받았고, `Application Services > Maps`의 `Directions 15`를 선택했다고 확인했다. 실제 인증·사용 권한과 조회 성공 여부는 아직 실행으로 검증하지 않았다.
- 기존 `API_SPEC.md`는 대중교통 `subway / bus`를 대상으로 하며 택시를 지원하지 않는다. 현재 코드의 더 넓은 이동수단 목록을 공개 계약의 자동차·택시 지원 근거로 삼지 않는다.
- 좌표 직접 제공과 Maps Directions 15 사용은 사용자 답변으로 확정되었다. FR-002의 적용 범위는 미확정이며, 이 답변을 반영하기 전까지 planning-ready가 아니다.
- 이번 단계에서는 명세와 품질 체크리스트만 작성한다. 연동 코드, 실제 API 호출, 공개 API 계약 변경, 배포 및 commit은 수행하지 않는다.
- 최소 연동안은 단일 출발지·단일 목적지의 기본 경로 조회다. 경유지, 다중 목적지, 경로 옵션 비교, 요금 표시·최적화, 지도 화면, 자동 감시 및 별도 사용자 클라이언트는 사용자가 추가로 범위를 정하지 않는 한 제외한다.
- 장소 검색·주소 변환은 사용자 답변에 따라 제외한다. 다른 교통 제공자, Hermes·MCP의 신규 기능 및 Solar 연동은 이번 네이버 기능의 범위에 포함하지 않는다. 대중교통 제공처 선정으로 방향을 바꾸는 선택은 별도 범위 확정이 필요하다.
- 적용 지역은 기존 제품 범위인 서울을 기본으로 하며, 실제 제공 가능한 경로는 제공처 응답으로 확인한다.
- 네이버 공식 문서는 2026-09-16 확인했다. Directions 15는 자동차 경로이며 조회 시점의 실시간 교통 정보를 반영한다. 공개 Maps 목록에는 대중교통 경로 데이터를 반환하는 API가 없다. 네이버 지도 앱의 대중교통 길찾기 URL Scheme은 앱을 여는 기능이므로 서비스의 경로 데이터 제공처로 사용하지 않는다.
