# 기능 명세: 이동 입력·조건 확인·출발 시각 계산

> 2026-09-14: 서비스 제공 형태는 MCP로 확정됐다. Hermes는 개발·시연용 클라이언트다. 기존 REST 스키마는 유지하며, 제품 전제의 정정은 구현·테스트 완료를 의미하지 않는다.


**기능 번호**: 001
**생성일**: 2026-09-13
**상태**: 초안

**입력 설명**: 사용자가 자연어로 약속 이동 요청을 입력하면, 필요한 이동 조건을 구조화하고 부족한 조건만 최대 3개까지 질문한 뒤, 실제 서울 교통 데이터로 출발시각과 계산 근거를 제공한다.

## 사용자 시나리오 & 테스트

### 사용자 스토리 1 — 약속 출발 시각 확인 (우선순위: P1)

사용자가 "오늘 오후 7시까지 강남역 2번 출구에 도착해야 해"라고 입력한다. 시스템이 출발지, 목적지, 도착 마감시각, 도착 여유, 이동수단을 확인하고, 부족한 정보만 최대 3개 질문한 뒤, 실제 교통 데이터로 권장 출발시각, 목표 도착시각, 경로, 계산 근거를 표시한다.

**우선순위 이유**: 서비스의 핵심 가치(언제 출발해야 하는지 안내)를 가장 직접적으로 제공하는 흐름이며, 다른 기능의 기반이 된다.

**독립적 테스트**: 자연어 입력 → 조건 확인 → 실제 데이터 기반 권장 출발시각 표시까지 하나의 흐름으로 검증할 수 있다. 목적지 도착 마감 시각이 명확한 경우, 추가 질문 없이 요약 확인 후 계산이 가능해야 한다.

**수용 시나리오**:

1. **Given** 사용자가 "오늘 19시까지 강남역 2번 출구에 도착해야 해"를 입력 **When** 해석 API 호출 **Then** arrival_deadline=19:00, destination.query="강남역 2번 출구"로 구조화하고 출발지 미확정을 질문한다.
2. **Given** 출발지·목적지가 모두 확정되고 arrival_deadline이 명확 **When** 사용자가 조건을 최종 확인 **Then** /journeys/plan 호출로 후보 경로와 권장 출발 시각을 반환한다.
3. **Given** 도착 여유가 미지정 **When** Hermes 확인 대화에서 적용 기본값(도착 여유 0분, 이동수단 subway·bus)을 표시 **Then** 사용자가 적용된 기본값을 확인하고 최종 동의한다.

### 사용자 스토리 2 — 막차로 귀가 시각 확인 (우선순위: P2)

사용자가 "막차로 집에 가려면 언제 나가야 해?"라고 요청한다. 출발지와 귀가 목적지를 확인한 뒤, 검증 가능한 범위 내에서 연결 가능한 마지막 이동편과 이론상 최종 출발 시각, 여유 적용 권장 시각을 구분해 표시한다.

**우선순위 이유**: 제품의 주요 차별화 지점(막차) 상황이나, 지원 가능한 노선·운행일·환승 연결 검증이 먼저 필요하다.

**독립적 테스트**: 출발지·목적지·운행일 입력 → 막차 가능 여부 확인 → 마지막 여정 시각과 권장 출발 시각 표시 흐름으로 검증한다. 지원 불가 시 LAST_JOURNEY_UNSUPPORTED로 안내한다.

**수용 시나리오**:

1. **Given** 막차 요청이며 출발지·목적지가 확인되고 운행일 지정이 필요 **When** 시스템이 운행일을 질문 **Then** service_date를 확정하고 검증 가능한 마지막 여정 계산을 수행한다.
2. **Given** 지원 데이터에서 연결 가능한 막차가 존재 **When** 계산 완료 **Then** hard_leave_at과 권장 출발 시각을 구분해 표시한다.
3. **Given** 요청한 운행일·노선·방향의 지원 데이터가 부족 **When** 계산 시도 **Then** LAST_JOURNEY_UNSUPPORTED로 안내하며 임의 막차 시각을 생성하지 않는다.

---

### 사용자 스토리 3 — 계획이 깨졌을 때 재탐색 (우선순위: P2)

사용자가 버스를 놓쳤거나 현재 위치가 바뀌어 재탐색을 요청한다. 현재 출발 기준점·시각과 유지할 목적지·마감시각을 확인한 뒤, 현재 조건에서 가능한 새 경로를 계산하고 이전 계획과 비교해 보여준다. 사용자는 새 계획을 선택해야 기존 계획에 적용한다.

**우선순위 이유**: 실제 사용 중 계획 변경이 발생할 때 다시 판단하는 기능은 서비스 신뢰도를 높이며, 사용자 확인 원칙을 지키는 핵심 흐름이다.

**독립적 테스트**: 기존 계획 존재 → 재탐색 요청 → 새 후보 계산 → 이전 계획과 비교 표시 → 사용자 선택으로 적용 여부 결정까지 검증한다.

**수용 시나리오**:

1. **Given** 사용자가 Hermes에서 "버스 놓쳤어. 다시 찾아줘"라고 요청 **When** 현재 출발 기준점과 시각을 확인 **Then** 현재 서버 시각 기준으로 새 경로를 계산한다.
2. **Given** 새 권장 후보 계산 완료 **When** 이전 계획과 비교 **Then** arrival_change_minutes, leave_change_minutes, 설명 문장을 표시한다.
3. **Given** 사용자가 새 계획을 선택 **When** 연동 계층이 현재 대화의 선택 계획을 갱신 **Then** 이전 기록은 삭제하지 않으며, 새 계획 적용 사실은 사용자 선택에 따른다.

---

### 사용자 스토리 4 — 이전 저장·상태 관리 요구 (현재 비적용)

2026-09-14 MCP 서비스 확정에 따라 영구 이동 저장·출발/도착 버튼·재시작 후 복원·알림 요구를 현재 범위에서 제외한다. US4 ID는 이력 참조용으로 남기며 구현·완료 조건으로 사용하지 않는다.

현재 대화의 확인 조건·선택 계획과 재탐색 후보 선택은 US1·US3 및 IDEA.md의 확인·문맥 원칙을 따른다. 상태 소유권·수명은 별도로 합의한다.

### 사용자 스토리 5 — 계산 근거·데이터 출처 확인 (우선순위: P3)

사용자가 MCP 도구 결과와 Hermes 설명에서 경로 구간, 예상 도착 시각, Safety Buffer 근거, 데이터 출처와 기준 시각을 확인할 수 있다.

**우선순위 이유**: 사용자가 결과를 신뢰하고 다음 행동을 판단하려면 계산 근거와 데이터 한계를 함께 볼 수 있어야 한다.

**독립적 테스트**: Plan 응답의 legs, buffer, sources, warnings가 MCP 결과에 유지되고 Hermes가 이를 정확히 설명하는지 검증한다.

**수용 시나리오**:

1. **Given** 계획 계산 완료 **When** 결과 표시 **Then** route 구간(walk/wait/subway/bus), estimated_arrival_at, buffer.items, sources.provider/basis/retrieved_at, warnings를 보여준다.
2. **Given** demo 출처가 하나라도 포함된 결과 **When** 표시 **Then** meta.is_demo=true와 DEMO_DATA 경고를 함께 표시한다.

---

### Edge Cases

- Deadline이 이미 지난 경우에도 이용 가능한 경로가 있으면 late 상태로 반환한다. 경로가 없으면 unavailable로 처리한다.
- "집", "잠실" 같은 모호한 표현은 임의 좌표로 확정하지 않고 장소 검색·선택으로 연결한다.
- 자정 경계를 넘는 이동은 날짜와 시간대를 포함해 처리하며, 막차의 경우 운행일과 실제 도착 날짜가 다를 수 있다.
- 도착 여유, 도보, 대기, 환승 시간이 이미 total_duration_minutes에 포함된 경우 별도로 다시 더하지 않는다.
- 요청 정보가 부족하면 최대 3개 질문을 한 번에 제공한다. 이미 확인된 조건을 반복해서 묻지 않는다.
- 교통 제공처 장애, 데이터 없음, 지원 범위 밖은 서로 다른 사유로 구분한다.
- 재탐색 실패·취소 시 기존 선택 계획을 삭제하지 않는다.
- 사용자가 다른 후보를 선택하면 비교 문구는 해당 비교에 맞지 않으므로 연동 계층은 해당 비교 문장을 숨기거나 다시 비교한다.

## 요구사항

### 기능 요구사항

- **FR-001**: 시스템은 사용자 자연어 입력에서 장소, 도착 마감 시각, 도착 여유, 이동 수단, 요청 종류(appointment/last_journey)를 구조화해야 한다.
- **FR-002**: 시스템은 부족한 또는 모호한 조건이 있을 때, 이번 응답에서 최대 3개의 질문을 제공해야 한다.
- **FR-003**: 시스템은 해석된 이동 조건(장소, 시각, 도착 여유, 이동 수단)을 사용자에게 요약 형태로 표시하고 최종 확인을 받은 뒤에만 계획 계산을 요청해야 한다.
- **FR-004**: 시스템은 place_id를 서버에서 실제 장소로 해석하며, 클라이언트가 임의 수정한 좌표로 교통 계산을 수행하지 않도록 해야 한다.
- **FR-005**: 시스템은 appointment의 목표 도착 시각을 arrival_deadline에서 arrival_preference_minutes를 뺀 값으로 계산해야 한다.
- **FR-006**: 시스템은 실제 교통 데이터(시간표·조회 결과 등)와 코드 기반 Buffer 규칙을 함께 적용해 후보 경로 1~3개와 권장 후보 ID를 반환해야 한다.
- **FR-007**: 시스템은 각 RouteOption에 경로 구간(legs), 권장 출발 시각, 예상 도착 시각, total_duration_minutes, buffer, 도착 상태, sources, warnings를 포함해야 한다.
- **FR-008**: 시스템은 Buffer 시간을 legs와 total_duration_minutes에 반영하고, 연동 계층에서 이를 다시 더하거나 권장 출발 시각에서 다시 빼지 않도록 해야 한다.
- **FR-009**: 시스템은 각 교통 결과에 데이터 출처(provider, basis, retrieved_at, service_date)와 경고(warning)를 포함해야 하며, demo 출처가 하나라도 있으면 meta.is_demo=true로 표시해야 한다.
- **FR-010**: 시스템은 막차 요청 시 hard_leave_at(검증된 이론상 최후 출발)과 권장 출발 시각을 구분해 반환해야 한다.
- **FR-011**: 시스템은 사용자 요청 재탐색 시 현재 서버 시각 기준으로 새 경로를 계산하고, 이전 계획과의 비교 정보(arrival_change_minutes, leave_change_minutes, summary)를 제공해야 한다.
- **FR-012**: 시스템은 재탐색 결과를 사용자가 선택하기 전까지 기존 계획에 적용하지 않아야 하며, 실패·취소된 재탐색이 기존 선택 계획을 삭제하지 않도록 해야 한다.
- **FR-013**: **현재 비적용**. 이전 영구 저장·출발/도착 상태·알림 요구이며 MCP MVP의 구현·완료 기준에서 제외한다.
- **FR-014**: **현재 비적용**. 이전 영구 저장·출발/도착 상태·알림 요구이며 MCP MVP의 구현·완료 기준에서 제외한다.
- **FR-015**: **현재 비적용**. 이전 영구 저장·출발/도착 상태·알림 요구이며 MCP MVP의 구현·완료 기준에서 제외한다.
- **FR-016**: **현재 비적용**. 이전 영구 저장·출발/도착 상태·알림 요구이며 MCP MVP의 구현·완료 기준에서 제외한다.
- **FR-017**: 시스템은 "집", "잠실" 같은 표현을 임의 장소로 확정하지 않고, 필요한 경우 장소 검색·선택 단계로 연결해야 한다.
- **FR-018**: 시스템은 데모와 실제 데이터를 구분해 표시하고, 운영 조회 실패를 데모 결과로 자동 대체하지 않아야 한다.

### Key Entities

- **TripDraft**: 사용자의 자연어 입력을 구조화한 이동 조건 초안. kind, origin, destination, arrival_deadline, arrival_preference_minutes, service_date, transport_modes, ambiguities를 포함한다.
- **TripRequest**: 계획 계산에 사용하는 확정된 이동 조건. place_id 기반이며 kind, origin_place_id, destination_place_id, arrival_deadline, arrival_preference_minutes, service_date, transport_modes를 포함한다.
- **Plan**: 계획 계산 결과. plan_id, generated_at, refresh_after, trip, origin, destination, target_arrival_at, recommended_option_id, options를 포함한다.
- **RouteOption**: 후보 경로 하나. option_id, summary, recommended_leave_at, hard_leave_at, estimated_arrival_at, total_duration_minutes, buffer, arrival_status, late_by_minutes, target_margin_minutes, legs, calculation_method, sources, warnings, navigation_url을 포함한다.
- **Leg**: 이동·대기 구간. leg_id, mode, from, to, departure_at, arrival_at, duration_minutes, transit, wait_reason을 포함한다.
- **Buffer**: Safety Buffer 정보. policy_version, total_minutes, items를 포함한다.
- **현재 대화의 선택 계획**: Plan과 selected_option_id를 재탐색에 전달한다. 영구 저장·진행 상태·알림 필드는 필수로 요구하지 않으며 저장 위치·수명은 합의한다.

## 성공 기준

### 측정 가능한 결과

- **SC-001**: 명확한 도착 마감 시각과 확정된 출발지·목적지가 있는 입력은 추가 질문 없이 요약 확인 후 계획 계산으로 진행할 수 있어야 한다.
- **SC-002**: 정보가 부족한 입력은 이번 응답에서 최대 3개의 질문으로 부족한 조건을 요청할 수 있어야 한다.
- **SC-003**: 사용자는 계산 결과에서 권장 출발 시각, 예상 도착 시각, 경로 구간, Safety Buffer 근거, 데이터 출처와 기준 시각을 확인할 수 있어야 한다.
- **SC-004**: **현재 비적용**. 이전 재시작 복원·진행 상태 관리 기준은 MCP MVP 완료 조건이 아니다.
- **SC-005**: 사용자 요청 재탐색은 이전 계획과 비교 정보를 제공하고, 사용자 선택 전에 기존 계획을 교체하지 않아야 한다.
- **SC-006**: demo 데이터와 실제 데이터는 meta.is_demo와 경고로 구분되어야 하며, 운영 조회 실패가 데모 결과로 자동 대체되지 않아야 한다.
- **SC-007**: 막차 지원 범위 밖이거나 연결 가능한 여정이 없으면 서로 다른 사유(LAST_JOURNEY_UNSUPPORTED / NO_FEASIBLE_JOURNEY)로 안내해야 한다.

## 가정

- 대상 지역은 서울이며, 실제 지원 범위는 검증된 교통 데이터의 지역·노선·운행일로 제한한다.
- 시간대는 Asia/Seoul만 허용하며, 날짜와 시간대를 포함해 처리한다.
- 도보·대기·환승 시간은 transport_modes로 제한하지 않고 연결 구간으로 기본 허용한다.
- taxi는 이번 MVP에서 지원하지 않는다.
- 서비스 제공 형태는 MCP다. Hermes + Solar Pro4를 개발·시연용 클라이언트로 사용하며 별도 제품 화면을 만들지 않는다.
- UserData DB·영구 이동 이력·회원가입은 필수 범위가 아니다. 저장·인증을 추가하려면 먼저 계약·권한을 합의한다.
- Buffer 정책의 실제 버전·수치는 첫날 검증 후 확정한다. 확정 전에는 가정이라는 사실을 결과에 표시한다.
- 막차 지원은 첫날 검증한 노선·운행일 범위에서만 제공한다. 지원 불가 시 해당 범위 제한을 명시한다.
- MVP 재탐색은 사용자 요청으로 시작한다. 자동 재탐색·백그라운드 재계산·GPS 상시 추적·Calendar 동기화·개인화 학습·전국 교통·자체 지도/Turn-by-turn Navigation은 제외한다.
- AI(Solar Pro4 등)는 입력 구조화, 확인 질문, 계산 결과 설명을 담당하며, 시간 계산·경로 유효성·상태 전이·횟수 제한·권한 검증은 검증 가능한 코드로 처리한다.
- 실제 교통편·막차시각·이동시간은 모델이 추측하지 않으며, 실시간 정보·막차·경로 데이터는 실제 API 응답으로 검증한 범위만 사용한다.

### MainAgent·SubAgent·Skill 실행 구조와 .hermes/skills/ 활용

- 이 구조는 개발자를 보조하는 코딩 에이전트 분업이 아니라, 제출할 서비스의 실행 구조다.
- MainAgent는 사용자 요청과 현재 상태를 파악해 적절한 SubAgent에 작업을 배정하고, 실행 순서·결과 취합·사용자 확인 요청을 조정한다.
- SubAgent에는 `.hermes/skills/`에 보관된 Skill을 역할에 맞게 할당한다. SubAgent는 해당 작업에 필요한 Skill을 선택해 사용한다.
- SubAgent와 Skill은 1:1 대응이 아니다. 하나의 SubAgent가 여러 Skill을 사용할 수 있으며, 모든 Skill을 매 요청마다 실행하지 않는다.
- 실제 SubAgent 목록과 Skill 묶음은 구현 계획에서 정한다. 기존 Skill이 있다는 이유만으로 보류 기능을 활성화하지 않는다.
- 경로 조회, 시간 계산, 상태 변경, 권한 검증 등 코드로 처리하는 것이 적합한 기능은 도구·도메인 로직으로 구현한다. 무리하게 별도 Agent를 할당하지 않는다.
- MainAgent·SubAgent 사이에는 검증 가능한 구조화 입력·출력을 사용한다. 구현 시 호출 횟수·전체 제한시간·실패 시 반환 규칙을 정하고 API 계약의 제한시간과 일치시킨다.

#### .hermes/skills/에 보관된 Skill과 역할별 사용 방향

Skill 원본은 `.hermes/skills/`에서 관리한다. 이번 공통 공유본에는 폴더 골격만 있으며, 로컬 ZIP은 포함하지 않는다. 원본을 별도로 검토·반입하기 전에는 실행 자산이 준비됐다고 간주하지 않는다. 아래 역할 예시는 IDEA.md와 agent_specs의 현재 MVP 범위가 우선한다.

- **이동 조건 해석·확정 SubAgent**: `.hermes/skills/resolve-trip-details`를 사용한다. 자연어에서 날짜·시간·출발지·목적지·출발/도착 의미·도착 여유시간·이동수단을 추출하고, 필요한 항목만 최대 3개 질문한 뒤 조건 요약을 만든다. 이 단계에서 경로 탐색·출발시각 계산은 하지 않는다.
- **약속 출발시각 안내 SubAgent**: 조건이 확정된 뒤 `.hermes/skills/leave-by`를 사용한다. 도착 Deadline, 목적지, 출발지, 도착 여유시간을 정리하고, 확인된 이동정보와 Safety Buffer를 반영해 권장 출발시각과 목표 도착시각을 안내한다. 정보가 부족하면 최대 3개까지만 질문한다.
- **막차 귀가 마지노선 SubAgent**: `.hermes/skills/maginot-line`을 사용한다. 현재 시각·출발지·목적지·택시 허용 여부를 확인하고, 권장 최종 출발시각과 이론상 최후 시각을 구분해 안내한다. 확인되지 않은 막차 시각·경로는 절대 지어내지 않는다.
- **일정 준비 확인 SubAgent**: `.hermes/skills/schedule-ready`를 사용한다. 일정이 이동 관리를 필요로 하는지 판단하고, 장소·오전/오후·출발지·도착 여유시간이 모호하면 최대 3개까지만 질문해 출발 시각 계산 전에 확정해야 할 정보를 정리한다.
- **계획 깨짐 대응 SubAgent**: `.hermes/skills/plan-b-recovery`로 현재 시각·현재 위치·목적지·도착 Deadline·놓친 교통편을 확인하고, 대중교통 유지·택시 혼합·Deadline 지키기 어려움의 세 상태를 구분해 대안을 제시한다. 이어서 `.hermes/skills/route-deviation`이 이탈 여부를 확인하고 재탐색 의사를 묻고, 승인 시 재탐색 요청 자료를 정리한다. 실제 재탐색 계산과 새 경로 제시, 자동 재제시 횟수 관리는 코드 기반 재탐색과 `.hermes/skills/replan-guard`가 담당한다.
- **계산 결과 설명 SubAgent**: `.hermes/skills/route-risk-checker`를 사용해 환승·도보·남은 시간·도착 여유시간을 기준으로 Deadline 위험을 진단하고, 위험도(낮음/보통/높음/판단 불가)와 판단 근거, 적용한 Safety Buffer, 주의할 구간, 권장 여유/행동, 추가 확인 정보를 제공한다. 이 결과는 별도의 성공 기준 항목이 아니라 계산된 결과의 위험·여유 설명에 통합한다.
- **사용자 진행 확인 Skill**: journey-check-in은 후속 상태 관리 확장용이다. 현재 MVP에서는 출발/도착 상태 관리 도구를 활성화하지 않는다.
- **알림 판단 Skill**: departure-alert은 후속 알림 확장용이다. 이번 MCP MVP에서 자동 알림·예약 발송을 구현하지 않는다.
- **후속 확장용 Skill(미사용)**: `.hermes/skills/taxi-hybrid`(대중교통만으로 어려울 때 필요한 구간만 택시 이용), `.hermes/skills/calendar-conflict`(여러 일정 사이 이동시간·충돌 확인), `.hermes/skills/replan-guard`(자동 재제시 횟수 관리와 사용자 승인)는 이번 MVP에서 활성화하지 않는다. 각각 후속 확장 또는 자동 재탐색 도입 시점에 적용한다.
