# 연구 노트: 이동 입력·조건 확인·출발 시각 계산

> 2026-09-14: 서비스 제공 형태는 MCP로 확정됐다. Hermes는 개발·시연용 클라이언트다. 기존 REST 스키마는 유지하며, 제품 전제의 정정은 구현·테스트 완료를 의미하지 않는다.


**생성일**: 2026-09-13
**목적**: 명세의 미확정 사항과 기술 선택을 정리하여 Phase 1 설계에 반영

## 1. 미확정 사항과 결정

### RC-01: Buffer 정책의 실제 버전과 수치

- **맥락**: 명세는 Buffer를 legs와 total_duration_minutes에 반영하고 연동 계층에서 중복 가산하지 않는다는 원칙을 명시했지만, 실제 정책 버전·수치는 첫날 검증 후 확정하도록 남겨뒀다.
- **결정**: 이번 계획에서는 `demo-v1`을 시연·Mock 기준 정책 버전으로 사용한다. 실제 정책은 교통 데이터 검증 후 확정하며, 확정된 버전·라벨·수치는 `capabilities.buffer_policy`와 Plan.response.buffer.policy_version에 반영한다.
- **대안 검토**: 정책 없이 매번 임의 Buffer를 계산하는 방안은 일관성 검증이 어려워 제외. 정책 버전 없이 고정 수치만 쓰는 방안은 향후 조정·검증 추적이 어려워 제외.

### RC-02: 막차 지원 범위(노선·운행일·검증 방식)

- **맥락**: IDEA.md는 막차를 첫날 검증한 지역·노선·운행일 범위에서만 제공하라고 명시. API_SPEC.md는 `last_journey.available`, `scope_note`, `service_date_from/to`로 지원 상태를 표현.
- **결정**: MVP 초기에는 capabilities에서 `last_journey.available`과 scope_note로 지원 여부를 반환하고, 지원 불가 시 `LAST_JOURNEY_UNSUPPORTED`, 지원 범위에서 경로가 없으면 `NO_FEASIBLE_JOURNEY`로 구분한다. 지원할 노선·운행일 범위가 확정되면 scope_note에 구체적 제약을 기록한다.
- **대안 검토**: 모든 서울 노선 막차를 기본으로 제공하는 방안은 검증 전 과대 약속이 되어 제외. 막차 검증을 완전히 보류하는 방안은 제품 핵심 축이라 제외.

### RC-03: MCP 서비스 제공과 담당 확정

- **결정일**: 2026-09-14.
- **결정**: 서비스 자체를 MCP로 제공한다. Hermes + Solar Pro4는 개발·시연용 클라이언트이며, 독립 사용자 클라이언트는 만들지 않는다.
- **구조**: 본인은 MCP 도구·HTTP 연결·확인/선택 흐름·시연, 친구는 FastAPI·Agent·계산·교통 데이터·배포를 담당한다.
- **범위**: 영구 이동 저장·출발/도착 버튼·알림은 현재 비적용이다. 대화별 확인 조건·선택 계획의 소유권과 수명은 구현 전에 합의한다.
- **이전 결정 대체**: 제품 형태를 멘토링 후 선택한다는 이전 결정을 폐기한다. 로컬 stdio와 원격 MCP 연결 방식의 검증은 제품 형태 선택과 별개다.

### RC-04: AI 호출 설정(모델·경로·제한시간·실패 정책)

- **맥락**: IDEA.md와 API_SPEC.md는 실행용 AI 모델 ID·호출 경로, 호출 제한을 미확정으로 남김. 계획은 호출 횟수·제한시간·실패 시 반환 규칙을 API 계약 제한시간과 일치시켜야 한다.
- **결정**: 현재 계획 단계에서는 AI 호출을 서버 내부 구현으로 두고, 공개 JSON 계약에는 영향 없게 유지한다. interpret API는 모델 미사용 시에도 수동 폼 입력으로 계산을 진행할 수 있어야 한다(AI_UNAVAILABLE 시 수동 입력 제공). 제한시간·실패 정책은 Mock/실제 전환 시 함께 확정한다.
- **대안 검토**: AI 호출을 명세에서 아예 제거하는 방안은 자연어 입력 흐름의 핵심이므로 제외.

### RC-05: 교통 제공처 어댑터 구성과 실제 데이터 검증 지점

- **맥락**: 교통 데이터는 서울시 공공데이터 포털·공공데이터 포털 API(발급된 키)를 사용. 실제 응답·지원 범위·한도·최신성은 첫날 검증 대상. API_SPEC.md는 Adapter로 공개 계약을 격리하라고 명시.
- **결정**: 백엔드 `integrations/`에 장소·교통 어댑터를 두고, 공개 계약(Post/Plan 응답 구조)은 어댑터 구현과 분리한다. Mock 모드에서는 examples.json의 case 응답을 사용하고, 실제 서버 연결 시 어댑터만 교체한다. Mock과 실제 서버의 JSON 구조는 동일하게 유지한다.
- **대안 검토**: Mock과 실제 응답을 별도 구조로 만드는 방안은 클라이언트 분기 증가로 제외.

### RC-06: 시간대·자정 경계·운행일/도착일 구분 처리

- **맥락**: Asia/Seoul만 허용, 날짜와 시간대를 포함, 막차는 운행일과 실제 도착 날짜가 다를 수 있음.
- **결정**: 모든 시각은 오프셋 포함 ISO 8601로 다루고, 계산 도구는 날짜와 시간대를 명시적으로 입력받는다. 막차는 service_date와 실제 도착 datetime을 분리해 다룬다. 자정 경계를 넘는 이동은 datetime 산술로 처리하고, 날짜 변경만으로 운휴·새로운 운행일로 간주하지 않는다.
- **대안 검토**: 시간대 변환을 클라이언트에서만 처리하는 방안은 서버 계산과 불일치 위험이 있어 제외.

## 2. 기술 패턴 결정

### TP-01: 계산 도구와 AI 역할 분리

- **결정**: 시간 계산, 경로 연결 유효성, 도보·대기·환승과 Buffer 중복 방지, 상태 전이, 횟수 제한은 코드 도구로 구현. AI는 TripDraft 생성, 질문 요약, 계산 결과 설명에만 사용.
- **근거**: 헌법 II·III 및 IDEA.md 7절과 일치.

### TP-02: 공개 계약 우선 구현

- **결정**: `/health`, `/capabilities`, `/places`, `/mobility/interpret`, `/journeys/plan`, `/journeys/replan`을 API_SPEC.md와 examples.json에 맞춰 먼저 구현한다. 필드·상태·오류 코드는 명세와 예제를 함께 갱신할 때만 변경.
- **근거**: 헌법 IV.

### TP-03: Mock 우선 통합, 실제 데이터 전환일 명확화

- **결정**: MCP 담당은 examples.json의 case id로 도구 결과·오류 전달을 먼저 검증하고, 백엔드는 실제 데이터 어댑터 연결 전 같은 JSON 구조를 유지한 채 Mock 응답을 반환한다. 실제 데이터 실패를 Mock으로 자동 대체하지 않는다.
- **근거**: 헌법 II·V, IDEA.md.

## 3. 미해결로 남긴 항목

- Buffer 정책의 실제 수치·버전, 막차 지원 노선·운행일 범위, AI 호출 설정, Base URL, 제공처별 한도와 최신성 기준은 첫날 검증·합의 후 확정한다.
- MCP 도구 스키마·사용자 확인·문맥 소유권과 수명은 공동 합의한다. UserData DB는 필수 범위가 아니다.
