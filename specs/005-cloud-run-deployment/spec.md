# Feature Specification: 무료 사용량 우선 Cloud Run 배포

**Feature Branch**: `feature/mcp-server-integrate` (현재 브랜치 유지, commit하지 않음)
**Feature Directory**: `specs/005-cloud-run-deployment`
**Created**: 2026-09-16
**Status**: 명세 확정 — 계획 비용 게이트 차단, 사용자 결정에 따라 서울 배포 보류
**Input**: “지금 세션에서는 GCP CloudRun 배포만 진행하겠습니다. 사용자는 가능하면 무료 플랜 한도 내에서 진행하기를 바랍니다. 연동을 위한 spec부터 수립합시다. 모호하거나 사용자 정보 제공이 필요한 사안은 질의를 해주십시오.”

## 준비 상태 판정 규칙

명세 작성, 설계 완료, 구현 완료, 원격 검증 완료를 각각 구분하여 기록한다. 선행 작업 목록 작성이나 설계 문서 완성만으로 구현·배포 준비 완료 또는 연결 성공을 선언하지 않는다. 비용 조건, 공개 계약 정합성, 저장·인증·복구 설계와 실제 구현 작업 목록이 모두 확정되기 전에는 구현 진입을 차단한다. 이 규칙은 FR-007·FR-014·FR-017과 성공 기준의 완료 판정을 구체화하며, 사용자 재개 요청이나 배포 승인을 대신하지 않는다.

현재 명세는 작성됐으나 비용 판정은 BLOCK-COST-001로 차단됐고 설계는 미완료다. 작업 목록은 설계 선행 목록만 존재하며 구현 완료·원격 검증 완료로 판정하지 않는다. 문서 정합성 보완은 서울 배포 보류와 월 추가 지출 0원 조건을 변경하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 원격 백엔드 연결 (Priority: P1)

개발자는 기존 계산 백엔드를 원격 환경에 배포하고, MCP 연동 담당자에게 접속 주소와 호출 조건을 전달할 수 있다. 원격 연결 성공과 실제 교통·모델 데이터 연동 성공은 구분한다.

**Why this priority**: 배포 주소의 존재만으로는 서비스 연결을 확인할 수 없다. 허용된 호출자가 기존 계약에 맞는 응답을 받아야 한다.

**Independent Test**: 배포 주소에서 허용된 호출자가 상태와 지원 범위를 조회하고, 기존 계약에 맞는 응답과 데모 표시를 확인한다.

**Acceptance Scenarios**:

1. **Given** 배포 환경과 호출 정책이 확정됐을 때, **When** 대상 버전을 배포하면, **Then** HTTPS 접속 주소·배포 버전을 확인하고 상태·지원 범위 조회에 성공한다.
2. **Given** 연동 담당자가 주소와 호출 조건을 받았을 때, **When** 그 조건으로 요청하면, **Then** 기존 요청·응답·오류 계약을 유지한 결과를 받는다.
3. **Given** 데모 제공자를 사용하는 버전일 때, **When** 원격 호출에 성공하면, **Then** 결과는 데모임을 유지하며 실제 교통·모델 연동에 성공했다고 표시하지 않는다.
4. **Given** 기동·설정·권한 문제로 서비스가 준비되지 않았을 때, **When** 검증하면, **Then** 실패 원인과 미검증 항목을 기록하고 연결 완료로 보고하지 않는다.

### User Story 2 - 무료 사용량 우선 비용 관리 (Priority: P1)

운영자는 무료 사용량을 우선 활용하고 별도 비용이 발생할 수 있는 항목, 지출 확인 방법, 사용 중단 방법을 배포 전에 이해한다.

**Why this priority**: 낮은 호출량만으로 전체 비용 0원을 보장할 수 없다. 빌드·이미지 저장·네트워크·상태 저장과 기존 계정 사용량을 함께 고려해야 한다.

**Independent Test**: 사용 자원별 무료 적용 조건·사용량 가정·예상 지출·통제 수단이 있는 비용 검토표를 합의한 월 지출 목표와 비교한다.

**Acceptance Scenarios**:

1. **Given** 프로젝트·결제 상태·예상 이용량이 확인됐을 때, **When** 비용을 검토하면, **Then** 반복되는 무료 사용량과 한시적 크레딧을 구분하고 결제 계정 내 다른 사용량을 반영한다.
2. **Given** 요청이 없는 유휴 상태일 때, **When** 용량 관리 정책이 적용되면, **Then** 상시 실행 용량을 유지하지 않는다. 유휴 후 첫 호출 지연 가능성은 안내한다.
3. **Given** 예상 비용이 합의 범위를 넘거나 새로운 유료 자원이 필요할 때, **When** 배포안을 검토하면, **Then** 비용·대안을 제시하고 사용자 결정 전 해당 자원을 만들지 않는다.
4. **Given** 지출 경고나 사용 중단 기준에 도달했을 때, **When** 운영자가 대응하면, **Then** 이번 배포의 사용을 줄이거나 중단할 수 있고 다른 서비스의 결제·자원을 임의로 변경하지 않는다.

### User Story 3 - 접근 범위와 대화 상태 일관성 (Priority: P1)

운영자는 누가 원격 서비스를 호출할 수 있는지 알 수 있고, 이용자는 재시작·재배포 이후 진행 중인 대화의 처리 방식을 예측할 수 있다.

**Why this priority**: 호출 범위는 보안·비용에, 상태 소실은 조건 확인·계획 선택·중복 요청 처리에 영향을 준다.

**Independent Test**: 합의한 허용·거부 호출과 재시작 전후 대화·선택·동일 요청 재전송 사례를 검증한다.

**Acceptance Scenarios**:

1. **Given** 팀 전용 호출 정책이 적용됐을 때, **When** 허가된 팀원 또는 MCP 호출자가 유효한 인증으로 접근하면, **Then** 정상 결과를 얻는다. 인증이 없거나 만료됐거나 호출 권한이 없는 요청은 계산과 상태 변경 전에 거부한다.
2. **Given** 확인 조건과 선택 계획이 있는 유효한 대화일 때, **When** 재시작 또는 재배포가 발생하면, **Then** 같은 대화 식별자·상태 버전·조건・후보·선택 계획·만료시각을 유지하고 사용자가 다시 입력하지 않아도 이어서 사용할 수 있다. 배포 자체가 유효기간을 연장하지 않는다.
3. **Given** 성공한 상태 변경 요청을 재시작 또는 재배포 후 재전송할 때, **When** 대화와 중복 요청 기록이 유효하면, **Then** 기존 계약에 따라 저장된 결과를 반환하고 같은 동작이나 상태 버전 증가를 두 번 적용하지 않는다.
4. **Given** 비밀 설정이 필요한 경우, **When** 배포·호출·오류 기록을 확인하면, **Then** 소스·이미지·문서·응답·로그에서 비밀값이 노출되지 않는다.
5. **Given** 대화 또는 후보의 유효기간이 지났을 때, **When** 재시작 이후 요청하면, **Then** 기존 계약의 만료 결과를 유지하고 만료된 상태를 되살리지 않는다. 후보만 만료되면 유효한 대화의 확인 조건·기존 선택은 보존한다.
6. **Given** 여러 실행 인스턴스나 배포 버전이 일시적으로 함께 요청을 처리할 때, **When** 같은 대화의 요청이 전달되면, **Then** 하나의 기준 상태에 따라 버전 충돌과 중복 요청을 처리하고 서로 다른 선택 계획을 성공 상태로 확정하지 않는다.
7. **Given** 상태 저장소에 일시적으로 접근할 수 없을 때, **When** 대화 상태를 사용하는 요청을 처리하면, **Then** 기존 계약의 해당 장애 결과를 반환하고 성공·만료로 위장하거나 빈 상태로 덮어쓰지 않는다.

### User Story 4 - 재배포와 복구 (Priority: P2)

다른 팀원도 안내에 따라 같은 버전을 배포하고 실패 시 이전 정상 버전으로 복구하거나 사용을 중단할 수 있다.

**Why this priority**: 최초 배포 이후 수정과 시연에서도 서비스와 비용을 통제할 수 있어야 한다.

**Independent Test**: 재배포 후 상태·지원 범위를 확인하고 이전 정상 버전으로 복구하는 절차를 검증한다.

**Acceptance Scenarios**:

1. **Given** 배포 안내와 권한이 있을 때, **When** 팀원이 대상 버전을 배포하면, **Then** 같은 공개 계약을 제공하고 사용한 버전을 식별할 수 있다.
2. **Given** 이전 정상 버전이 있을 때, **When** 새 버전의 필수 확인이 실패하면, **Then** 이전 정상 버전으로 복구할 수 있다. 최초 배포 실패는 서비스 사용 가능으로 보고하지 않는다.
3. **Given** 데모 운영을 종료할 때, **When** 중단 안내를 따르면, **Then** 호출을 중단하고 남아 있는 저장·빌드 자원과 비용을 식별할 수 있다. 삭제는 별도로 승인받는다.

### Edge Cases

- 프로젝트·결제 계정·필수 권한이 없거나 조직 정책이 원격 호출을 제한하는 경우.
- 같은 결제 계정의 다른 프로젝트가 무료 사용량을 이미 소비한 경우, 체험 크레딧이 소진되는 경우.
- 요청 급증·긴 요청·반복 빌드·이미지 누적·외부 통신으로 비용이 증가하거나 비용 표시가 지연되는 경우.
- 인증 만료로 MCP 호출이 거부되거나 유휴 후 첫 호출이 늦어지는 경우.
- 실행 진입점이나 지정 포트 불일치로 배포 버전이 준비되지 않는 경우.
- 재시작·재배포·동시 인스턴스 실행 중 대화와 중복 요청 기록이 사라지거나 서로 달라지는 경우.
- 대화 유효기간과 후보 유효기간이 다른 경우. 배포 편의를 위해 기존 만료 규칙을 바꾸지 않는다.
- 원격 HTTP 연결은 검증했지만 MCP 소스·Hermes 환경이 없어 전체 연동을 검증할 수 없는 경우.
- 사용 제한 기능이 실행을 중단했지만 이미지 저장 등 다른 비용은 계속 발생하는 경우.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 기존 계산 백엔드의 GCP Cloud Run 배포와 로컬 MCP 연동에 필요한 주소·호출 조건·검증 결과 제공을 범위로 삼아야 한다. 원격 MCP 서버 신규 배포는 포함하지 않는다.
- **FR-002**: 대상 버전·프로젝트·리전·서비스 식별자·접속 주소를 식별할 수 있어야 한다. 확인하지 않은 값을 실제 배포 정보로 기록하지 않아야 한다.
- **FR-003**: 배포 전 기동·환경 호환성과 기존 계약을 검증해야 한다. 공개 필드·오류·사용자 확인·후보 선택 규칙을 배포 편의를 위해 변경하지 않아야 한다.
- **FR-004**: 원격 결과의 데모 여부와 데이터 출처를 보존해야 한다. 이번 배포를 실제 교통·모델 연동 완료로 설명하지 않아야 한다.
- **FR-005**: 예상 월 호출 수·처리 시간·응답 크기·빌드 빈도·이미지 보관량·상태 저장량을 사용해 비용을 검토해야 한다. 실제 사용하는 모든 과금 자원을 포함해야 한다.
- **FR-006**: 무료 사용량을 우선 활용하고 요청이 없을 때 상시 실행 용량을 유지하지 않아야 한다. 실행 용량·처리 시간·빌드 빈도·보관량 제한과 첫 호출 지연을 계획에서 구체화해야 한다.
- **FR-007**: 사용자 제공 대상은 `project-jigeum` (프로젝트 번호 `670549467351`)이며 월 추가 지출 목표는 **0원**이다. 배포 전 프로젝트 ID와 번호의 일치, 결제 계정 연결·유형·활성 상태, 무료 사용량 적용 및 잔여분을 확인해야 한다. 사용자의 “무료 플랜” 표현만으로 무료 체험 계정 또는 유료 결제 계정이라고 단정하지 않아야 한다. 예상 추가 지출이 0원을 초과하는 배포안은 진행하지 않고 무료 범위의 대안이나 범위 축소를 먼저 제시해야 한다.
- **FR-008**: 비용 알림과 실제 사용 중단 수단의 차이·적용 범위·반영 지연·잔여 비용을 문서화해야 한다. 알림이나 실행 용량 제한을 전체 청구액의 절대 상한으로 설명하지 않아야 한다. 추가 비용이 필요한 변경은 사용자 결정 후 진행해야 한다.
- **FR-009**: 원격 백엔드는 팀 전용으로 제공하고, 허가된 팀원과 MCP 호출자만 유효한 인증으로 호출할 수 있어야 한다. 익명·인증 만료·권한 없는 호출은 계산과 상태 변경 전에 거부해야 한다. 구체적인 호출 주체와 인증 방식은 계획 단계에서 확정하며 비밀키 공유를 전제로 하지 않는다.
- **FR-010**: 재시작·유휴 종료·재배포 후에도 기존 유효기간 동안 대화 식별자·상태 버전·해석 및 확인 조건·후보·선택 계획·중복 요청 처리 기록을 보존해야 한다. 사용자의 조건 재입력을 정상 복구 절차로 요구하지 않아야 한다. 기존 만료·삭제 정책을 유지하며 배포로 상태 수명을 연장하거나 만료 상태를 되살리지 않아야 한다.

- **FR-017**: 기존 로컬 변경과 다른 기능의 명세를 보존해야 한다. 이번 명세 수립을 클라우드 자원 생성·권한 변경·배포의 승인으로 해석하지 않아야 한다. commit은 언제나 사용자의 명시적 허가 후 수행해야 한다.
