# 구현 계획: 무료 사용량 우선 Cloud Run 배포

**브랜치**: `feature/mcp-server-integrate` | **날짜**: 2026-09-16 | **명세**: [spec.md](spec.md)

**상태**: Phase 0 비용 게이트 차단 — 사용자가 0원 목표 유지 및 서울 배포 보류를 확정. 미답변 없음. Phase 1 미진행, 구현·배포 준비 완료 아님.

**입력**: `specs/005-cloud-run-deployment/spec.md`

## 요약

기존 FastAPI 계산 백엔드를 Cloud Run에 배포하고 로컬 Hermes → 로컬 MCP → HTTPS 백엔드로 연결한다. 팀원 2명, 하루 합계 100회 이하, 약 1개월의 시연을 기준으로 월 추가 지출 0원을 검토한다. 인증된 팀원만 호출하며 유효한 대화·조건·후보·선택 계획·revision·중복 처리 기록을 재시작과 재배포 후에도 유지한다.

현재 검토안은 서울(`asia-northeast3`)의 요청 기반 Cloud Run과 같은 리전의 Firestore Native Standard다. 사용자는 유료 계정이고 크레딧이 소진됐으며 별도 팀용 Google 계정에서 진행한다고 확인했다. 실제 계정 조회는 아직 하지 않았다. 서울발 인터넷 응답은 무료 전송량 범위에 포함되지 않으므로 월 추가 지출 0원 조건을 충족하지 못한다. 유료 계정 보유를 지출 승인으로 해석하지 않는다. 검토안은 자원 생성·권한 변경·배포·커밋 승인이 아니다.

### 확정된 차단 사유와 처리

- **BLOCK-COST-001**: 서울 Cloud Run → 인터넷의 로컬 MCP 응답 전송은 유료이며, 크레딧이 소진된 상태에서 FR-007/SC-002의 예상 추가 지출 0원 조건을 충족하지 못한다. [Cloud Run 공식 요금](https://cloud.google.com/run/pricing), [무료 사용량 조건](https://docs.cloud.google.com/free/docs/free-cloud-features).
- **사용자 결정**: 2026-09-16 “0원 유지: 서울 배포는 보류하고 계획에 차단 사유 기록”. 소액 지출 목표로 변경하는 안은 채택하지 않았다.
- **처리**: Phase 0 조사와 BLOCK-COST-001을 보존한다. 사용자 요청에 따른 선행 작업 목록 작성과 문서 분석·정합성 보완은 수행했다. 현재 tasks.md는 최종 구현 목록이 아니다. Phase 1의 완료, 서울 배포, 구현 실행 및 클라우드 자원·권한 변경은 계속 보류한다. 추가 문서 작성이나 분석 요청을 배포 재개 또는 지출 승인으로 해석하지 않는다. commit은 별도 명시 허가가 필요하다.
- **재개 조건**: 사용자의 명시적 재개 요청 후 비용 게이트를 해소하는 제약 변경 또는 검증 가능한 새 무료 조건이 있어야 한다. 실제 결제·무료 잔여량·기존 DB와 선행 계약 구현도 그때 다시 확인한다. 미국 리전이나 유료 대안으로 자동 전환하지 않는다.

## 기술 환경

| 항목 | 확인한 내용 또는 결정 상태 |
|---|---|
| 언어/버전 | Python 3.11, 기존 Docker 기반 |
| 주요 의존성 | FastAPI, Uvicorn, Pydantic 2, SQLAlchemy 2, httpx; Firestore SDK 추가는 설계 확정 후 구현 대상 |
| 현재 저장 | SQLite 설정·SQLAlchemy 모델은 존재하나 HTTP 상태 변경 경로에 저장 연동이 완성되지 않음 |
| 원격 저장 검토안 | 동일 리전 Firestore Native Standard `(default)`; 기존 무료 대상 DB·리전 확인 필요 |
| 테스트 | 기존 pytest unit/contract/integration + Firestore emulator 원자성 검사 + 승인된 원격 검증 |
| 플랫폼/유형 | Linux 컨테이너, Cloud Run의 내부 계산 HTTP 서비스; MCP는 로컬 별도 실행 |
| 성능 | cold start 허용. 처리 시간·메모리·응답 크기를 측정해 비용 산정에 반영; 미측정 지연을 SLO로 약속하지 않음 |
| 실행 후보 | request-based, min=0, service max=1, 1 vCPU, 512 MiB, 동시 처리 1, 요청 timeout 60초. 부하/기동 검사 후 확정 |
| 범위 | 2명 × 팀 합계 최대 100회/일, 30일 환산 최대 3,000회. 재시도·검증 호출도 별도 합산 |
| 필수 제약 | 추가 지출 목표 0원, 팀 인증, PORT/0.0.0.0, Asia/Seoul 업무 시각, 만료·확인·선택 계약 유지 |
| 인증 주체 | 사용자가 준비한 팀용 Google 계정. 개인별 계정을 새로 만드는 것을 전제로 하지 않음. 실제 principal과 IAM 권한은 배포 전 확인 |
| 비용 결정 | 0원 유지·서울 배포 보류 확정. 미답변 없음. BLOCK-COST-001 미해소 |

현재 기동 문제는 `backend/` build context에 맞지 않는 `backend.app.main:app` import 경로와 고정 `8000` 포트다. 계획한 build context는 `backend/`, 앱 경로는 `app.main:app`, 수신 포트는 주입된 `PORT`다. 아직 컨테이너 실행으로 검증하지 않았다.

### 사용자 확인 사항

- 팀원 2명, 하루 합계 100회 이하, 약 1개월 시연.
- 만료 후에는 즉시 재사용을 차단하되, 물리적 정리는 다음 시작·요청에서 수행해도 됨.
- tombstone이 있으면 410, 삭제됐거나 처음부터 없는 ID는 404로 구분.
- 서울 리전, 유료 계정, 크레딧 소진, 별도 팀용 Google 계정에서 진행.
- 서울발 전송료 확인 후 0원 목표 유지와 서울 배포 보류를 선택. 추가 비용 불허.

### 선행 작업과 범위 경계

1. 기존 상태 API 계약을 구현하는 담당 작업에서 실제 대화 생성, 조건 확인, 후보/선택 저장, revision 및 idempotency 원자성을 제공해야 한다. 현재 `/interpret`의 `revision=1`·매번 계산한 만료 메타데이터나 `/plan`의 응답만으로 저장 성공을 간주하지 않는다.
2. 이번 기능은 그 상태 연동을 원격 영속 저장으로 연결하고 재시작/재배포를 검증한다. 누락된 기존 공개 기능이나 새 확인·선택 API를 배포 편의로 임의 추가하지 않는다. 기존 작업 산출물을 확인한 뒤 연결 위치를 확정한다.
3. API 문서·예제의 404/410 및 cleanup 규칙은 사용자 선택안으로 공동 정합성을 확인한 후 구현한다. 이 계획은 `API_SPEC.md`의 충돌을 조용히 무시하지 않는다.
4. 재개 조건 확인(T003) 후 허용된 읽기 전용 범위에서 실제 프로젝트·DB·무료 한도·결제를 확인(T004)하고, 전체 사용 예정 자원의 비용을 산정하여 최종 비용 게이트를 판단(T009)한다. 이 근거 수집은 배포 승인이 아니다. 미조회·근거 부족·0원 초과이면 이후 설계·구현·클라우드 변경을 차단한다. 현재 PATH에서 `gcloud`가 발견되지 않았으며 로그인/계정 조회/설치하지 않았다.

### 기존 상태 API 선행 조건 확인표

T005에서 두 개발자가 아래 항목의 담당자, 기능 경로·작업 ID, 합의된 계약 버전, 구현 위치와 검증 근거를 연결한다. 현재 참조와 증거는 미확정이며 모두 차단 상태다. 예측한 작업 ID나 성공 결과로 채우지 않는다. 필요한 공개 계약 변경은 공동 합의와 `API_SPEC.md`·`Docs/api/examples.json` 갱신을 선행한다.

| 선행 조건 | 연결할 정보 | 통과 기준 | 현재 상태 |
|---|---|---|---|
| 대화 생성·복원 | 담당자·기능/작업·계약·구현·검증 기록 | 동일 ID로 저장 상태 복원 | 미확정·차단 |
| 사용자 확인·후보 선택 | 담당자·기능/작업·계약·구현·검증 기록 | 확인 전 계산 및 선택 전 적용 방지 | 미확정·차단 |
| revision | 담당자·기능/작업·계약·구현·검증 기록 | 동시 변경에서 충돌 검출 | 미확정·차단 |
| idempotency | 담당자·기능/작업·계약·구현·검증 기록 | 동일 요청 재전송의 중복 변경 방지 | 미확정·차단 |
| 만료·정리 | 담당자·기능/작업·계약·예제·검증 기록 | tombstone 410, 없는 기록 404, 시작·요청 시 정리 | 미확정·차단 |
| 저장 장애·원자성 | 담당자·기능/작업·계약·구현·검증 기록 | 부분 성공·빈 상태 덮어쓰기 방지 | 미확정·차단 |

기존 기능 구현의 누락을 배포 작업에서 임의로 대신 구현하거나 새 API로 보완하지 않는다. 선행 조건의 문서 연결과 실제 구현·검증 통과도 구분한다.

## 프로젝트 구조

### 팀원 연동 요청 반영

2026-09-16 받은 다섯 영역의 요청과 현재 확인 결과는 [연동 인수인계 확인표](handoff.md)에 모았다. FR-015·SC-006의 전달 항목을 구체화한 문서이며 Phase 1 계약·quickstart나 실행 가능한 배포 안내가 아니다. 미배포 URL, Secret 이름·버전, 서비스 계정, 배포 지원 여부는 임의로 채우지 않는다.

재개 후에는 API 호출자와 Secret을 읽는 실행 계정을 분리해 확인하고, 필요한 Secret만 이름·버전·용도·주입 방식으로 기록한다. Secret Manager를 사용할 경우 버전 수·접근 횟수 등도 비용 검토에 포함한다. 최신 소스의 confirm·상태·idempotency 지원, 실제 provider 연결, OpenAPI와 예제 JSON의 일치를 배포 버전 기준으로 다시 검증한다. 기존 `Docs/BACKEND_HANDOFF.md`의 초기 골격·SQLite·만료 410 통일 설명도 공동 계약 정합성 확인 대상에 포함한다.

```text
│   ├── db.py                          # 현재 SQLAlchemy 경계

│   ├── api/{mobility,journeys}.py       # 기존 상태 흐름 선행 작업과 연결
│   ├── services/conversation_service.py
│   ├── services/idempotency_service.py
│   └── storage/                       # Firestore adapter 후보, 확정 전
└── tests/{unit,contract,integration}/
Docs/                                 # 최종 연동·배포 안내 위치 후보
```

여러 저장소를 위한 범용 framework는 만들지 않는다. 실제 상태 경로를 확인한 후 필요한 작은 저장 경계만 둔다. 로컬 MCP 코드는 이 저장소에서 확인되지 않았으므로 토큰 갱신·재시도 동작을 계약으로 넘기며 해당 저장소를 구현 완료로 표시하지 않는다.

### Spec Kit 실행 기록

- `SPECIFY_FEATURE_DIRECTORY=specs/005-cloud-run-deployment`로 `setup-plan.ps1 -Json`을 실행했다.
- 반환된 FEATURE_SPEC/IMPL_PLAN/FEATURE_DIR는 이 폴더와 일치했다. 스크립트 BRANCH 값 `005-cloud-run-deployment`는 기능 식별자 fallback이며 실제 Git 브랜치 변경이 아니다.
- setup helper가 공용 `.specify/feature.json`도 자동 변경하는 것을 확인해 기존 `specs/004-public-transit-api-integration` 값으로 즉시 복원했다. 후속 읽기 전용 경로 검증은 `check-prerequisites.ps1 -PathsOnly`를 사용한다.
- `specs/005-naver-directions-integration`도 존재하므로 숫자 prefix만으로 기능을 선택하지 않는다.
- before_plan 및 after_plan 확인 시 `.specify/extensions.yml`은 없었다. 실행한 extension hook은 없다.

## 복잡성 검토

현재 승인된 헌법 예외는 없다. Firestore는 재시작 후 상태 보존 요구에서 도출한 후보이며 SQLite 로컬 파일 유지나 Cloud SQL 상시 비용을 피하기 위한 검토다. 비용 목표 충돌이 해소되기 전 Phase 1 설계를 완료로 표시하지 않는다. 기존 공개 상태 기능과 API 문서/fixture 정합성은 구현 선행 게이트로 유지한다.

## 검증 계획

1. 문서: 사용자 결정 추적, 공개 계약 영향, 파일 링크, 미확정 사항과 실행 증거 구분.
2. 구현 후 로컬: 기존 backend pytest, PORT를 8000 이외로 주입한 Docker 기동, 비밀/DB/build context 제외 확인. 소스·이미지 계층·설정 예제·문서 및 정상/제공처 장애/저장 장애 시의 로그·응답도 점검한다. 동작 검증에는 가짜 인증 문자열·가짜 키/자격증명을 사용하고 노출 0건을 합격 기준으로 삼는다. 실제 비밀값은 점검 결과에 복사하지 않으며 미점검 대상이 있으면 SC-003 미통과다.
3. 저장: 동일 key replay, 다른 payload 충돌, stale revision, 동시 갱신, 만료·candidate만 만료, 저장 장애, 부분 커밋 방지. emulator는 비용/IAM을 검증하지 못함을 표시.
4. 승인된 클라우드 검증: 권한별 허용/거부, health/capabilities 각각 3회, 재시작·재배포 각 1회 상태 유지, 이전 정상 revision으로 복구 1회.
5. 비용: 모든 실제 자원·응답 egress·빌드/이미지/로그/상태 저장의 사용량을 무료 잔여량과 비교. 예측만으로 SC-002 검증 완료를 선언하지 않음.
