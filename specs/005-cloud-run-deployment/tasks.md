# 작업 목록: Cloud Run 배포 재개 조건과 설계 선행 작업

**작성일**: 2026-09-16
**입력**: [spec.md](spec.md), [plan.md](plan.md), [research.md](research.md), [handoff.md](handoff.md), `../../.specify/memory/constitution.md`
**상태**: 배포 보류 유지. 구현용 작업 목록 확정 전의 선행 작업 목록.

사용자는 서울 리전, 크레딧이 소진된 유료 계정, 팀용 Google 계정, 월 추가 지출 0원 및 서울 배포 보류를 확정했다. 이번 tasks 작성 요청은 문서 생성에 대한 요청이며 비용 변경·배포 재개 승인이 아니다. `BLOCK-COST-001`은 그대로 유지한다.

현재 계획은 Phase 0에서 차단됐으며 `data-model.md`, `contracts/`, `quickstart.md`가 없다. 이 파일들은 모든 프로젝트에 필수인 문서가 아니지만, 이 기능은 상태 원자성·인증·복구 설계가 아직 확정되지 않아 구현 작업을 안전하게 구체화할 수 없다. Firestore와 서비스 계정 토큰 방식은 후보이며 확정된 의존성으로 취급하지 않는다.

**실행 제한**: 아래 18개 항목은 미완료다. 현재 배포 보류를 유지한다. T001~T002는 현재 보류 상태에서 문서 확인으로 실행 가능하다. 재개 요청이 있을 때 T003에서 재개 조건을 확인하고, 허용된 근거 수집 범위에서 T004·T009를 수행한다. 최종 비용 게이트 통과 전에는 이후 설계·구현·클라우드 변경을 진행하지 않는다. 근거 수집에 자원 생성이나 유료 실행이 필요하면 자동으로 수행하지 않는다. 과금 API 호출·자원 생성·IAM/Secret 변경·배포는 구체적 실행안에 대한 승인 범위를 별도로 확인한다. commit은 항상 별도 명시 허가가 필요하다.

Skill의 “The tasks.md should be immediately executable” 조건을 전체 구현 작업에 대해 충족했다고 주장하지 않는다. 사용자 보류 결정과 불완전한 설계를 우선하여 선행 작업을 기록한 것이다. 스토리별 항목은 설계·검증 준비이며, 완료해도 원격 서비스 구현 또는 명세의 성공 기준 통과를 의미하지 않는다.

## Phase 1: 준비 — 현재 수행 가능한 문서 확인

**목표**: 기능을 정확히 선택하고 재개 시 사용할 증거와 보류 조건을 확인한다.

- [ ] T001 `specs/005-cloud-run-deployment/plan.md`의 BLOCK-COST-001, 0원·서울·배포 보류 결정, commit 제한을 `specs/005-cloud-run-deployment/spec.md`와 대조하고 재개 조건에 모순이 있으면 문서에 기록한다.
- [ ] T002 `specs/005-cloud-run-deployment/handoff.md`의 배포 정보·MCP 인증·Secret 설정·API 계약·연결 테스트 준비 다섯 영역을 FR-015/SC-006과 대조하고 미확인 항목을 성공 또는 실제 값으로 채운 부분이 없는지 확인한다.

**완료 기준**: 보류 상태와 필요한 정보가 일치하고, 원격 주소·권한·Secret·검증 성공을 추정하지 않는다.

## Phase 2: 기반 — 재개 후에만 수행하는 차단 해소

**선행 조건**: 사용자가 재개를 명시적으로 요청함. 현재 서울·크레딧 소진·0원 조건이 그대로이고 새로운 무료 적용 근거도 없다면 T003에서 다시 멈춘다. 사용자 답변을 임의 생성하지 않는다. T004와 T009는 최종 비용 판정에 앞선 근거 수집이며, 읽기 전용 조회 허용을 배포 승인으로 해석하지 않는다.

- [ ] T003 사용자 재개 요청과 변경된 조건 또는 새로운 무료 적용 근거, 허용된 읽기 전용 조회 범위를 확인하고 `specs/005-cloud-run-deployment/plan.md`에 기록한다. 기존 서울·크레딧 소진·0원 조건과 알려진 비용 충돌이 그대로이며 새로운 근거도 없으면 BLOCK-COST-001을 유지하고 T004 이후를 실행하지 않는다. 재개 조건 확인을 최종 비용 게이트 통과로 표시하지 않는다.
- [ ] T004 승인된 접근 환경에서 프로젝트 ID/번호·결제 연결·공유 무료 잔여량·기존 DB 리전·이미지 보관량을 읽기 전용으로 확인하고 비밀값 없이 `specs/005-cloud-run-deployment/research.md`에 확인 시각·근거·미조회 항목을 기록한다. 로그인·권한 부족은 실패로 구분하며 설치나 권한 변경으로 자동 우회하지 않는다.
- [ ] T005 T009의 최종 비용 판정 통과 후 `API_SPEC.md`, `Docs/api/examples.json`, 현재 상태 API 구현을 대조하고 두 개발자 공동 정합성 확인 결과를 `specs/005-cloud-run-deployment/plan.md`의 선행 조건 확인표에 기록한다. 대화 생성·복원, 확인/선택, revision, idempotency, tombstone410/없는 기록404·시작/요청 정리, 저장 장애·원자성 각각에 담당자·기능 경로/작업 ID·합의된 계약 버전·구현 위치·검증 근거를 연결한다. 미확정은 차단 상태로 남기고 실제 구현·검증 통과와 문서 연결을 구분한다. 누락 기능을 배포 작업에서 임의로 구현하거나 새 API로 보완하지 않으며 공개 계약 변경은 공동 합의와 API 문서·예제 갱신을 선행한다.

**완료 기준**: 비용 게이트 통과 근거와 상태 계약의 담당·선행 조건이 명확하다. 실제 계정 조회가 무료 사용량·향후 청구액 보장을 뜻하지 않음을 구분한다.

**목표**: 계약을 보존하는 컨테이너·HTTPS 연결과 인수인계 설계를 확정한다.
**독립 검증 기준**: 향후 승인된 배포본의 health/capabilities를 허용된 호출자가 각각 3회 연속 조회하여 계약과 demo 표시를 확인한다(SC-001). 아래 작업은 그 검증의 준비다.

- [ ] T006 [US1] `backend/Dockerfile`과 `backend/app/main.py`를 다시 확인하고 build context, import 경로, PORT/0.0.0.0, 제외 파일, 실행 버전 식별 방법을 `specs/005-cloud-run-deployment/plan.md`에 확정한다. 필요한 코드 수정 위치를 기록하고 이 설계 작업에서 코드는 수정하지 않는다.
- [ ] T007 [US1] `specs/005-cloud-run-deployment/contracts/backend-connection.md`에 `/api/v1` 기본 주소, `/openapi.json`, 인증 실패와 backend envelope 차이, 업무 헤더·동일 요청 재시도 책임을 정의한다. 실제 URL은 승인된 배포 후 채우는 값으로 표시한다.
- [ ] T008 [US1] `specs/005-cloud-run-deployment/quickstart.md`에 비기본 PORT Docker 기동, 소스·배포 파일·이미지 계층·설정 예제·문서의 비밀값 및 로컬 DB/개인 설정 제외 점검, 원격 health/capabilities 각 3회와 demo 표시 검증의 명령·예상 결과·실패 기록 방식을 작성한다. SC-003의 대상·방법·실행 버전·결과 기록 형식을 정의하고 비밀값 자체를 결과에 복사하지 않는다. 명령 작성과 실제 실행 결과를 구분하며 미점검 대상이 있으면 통과로 판정하지 않는다.

## Phase 5: US3 — 팀 접근과 대화 상태 일관성 설계 (P1)

**목표**: 영속 상태·원자성·만료·최소권한을 확정한다.
**독립 검증 기준**: 허용/거부 인증 사례 및 재시작·재배포 각1회 상태 보존, replay 중복 변경0건, 만료·후보만 만료·동시 수정·저장 장애 각1회가 명세와 일치한다(SC-003/004).

- [ ] T012 [US3] `specs/005-cloud-run-deployment/data-model.md`에 확정된 저장 방식의 대화·해석/확인 조건·후보·선택 계획·revision·만료·idempotency 응답 기록을 정의한다. 상태 변경과 성공 기록의 원자적 단위, 원본 payload 제거, tombstone24시간 및 child 기록 정리, 용량 제한, 재배포 schema 호환성을 명시한다. 영구 이력·회원가입은 추가하지 않는다.
- [ ] T013 [US3] `specs/005-cloud-run-deployment/contracts/access-and-state.md`에 팀 Google principal·호출 SA·실행 SA·배포 주체의 권한 경계, audience·토큰 갱신, Secret 접근과 API 인증의 구분, 만료/replay/revision 우선순위 및 저장 장애 의미를 정의한다. 실제 비밀값·자격증명 파일·토큰을 포함하지 않는다.
- [ ] T014 [US3] `specs/005-cloud-run-deployment/quickstart.md`에 인증 거부, 재시작/재배포 상태 비교, 동일 key replay·다른 payload 충돌, 동시 갱신·만료·후보만 만료·저장 장애·부분 커밋 방지의 준비 입력과 기대 결과를 작성한다. 가짜 인증 문자열·가짜 키/자격증명으로 정상 처리 및 제공처/저장 장애를 로컬에서 재현하고 로그·정상 응답·오류 응답의 비밀값 노출 0건을 점검하는 절차를 추가한다. 대상·방법·실행 버전·결과를 기록하되 비밀값은 복사하지 않고 미점검 대상은 SC-003 미통과로 남긴다. emulator 원자성 검사와 실제 IAM/비용 검증 범위를 구분하며 원격 실행은 승인 전 수행하지 않는다.

## Phase 6: US4 — 재배포와 복구 설계 (P2)

**목표**: 호환 저장 상태를 유지하면서 정상 revision으로 복구하고 사용을 중단할 수 있게 한다.
**독립 검증 기준**: 승인된 환경에서 이전 정상 revision으로 복구1회 후 health/capabilities가 정상이며 실행 근거가 남는다(SC-005/006).

- [ ] T015 [US4] `specs/005-cloud-run-deployment/plan.md`에 배포 버전/이미지 digest 식별, 이전 정상 이미지 확보, 저장 schema 호환 조건, traffic rollback과 데이터 rollback의 차이, 호출 중단·잔여 저장 비용 확인 절차를 정의한다. 파괴적인 migration이나 자원 삭제는 자동 실행 절차로 넣지 않는다.
- [ ] T016 [US4] `specs/005-cloud-run-deployment/quickstart.md`에 재배포·이전 정상 revision 복구1회·상태 조회 및 잔여 자원 확인 시나리오를 작성하고 `specs/005-cloud-run-deployment/handoff.md`에 결과를 인계할 증거 형식을 연결한다. 원격 미실행 항목은 미검증으로 유지한다.

## 의존성과 실행 순서

```text
T001 → T002
사용자 재개 요청
  → T003: 재개 조건 확인
  → T004: 허용된 계정 근거 확인
  → T009: 비용 산정·최종 게이트
  → 통과한 경우에만 T005
  → US2: T010 → T011
  → US3: T012 → T013 → T014
  → US1: T006 → T007 → T008
  → US4: T015 → T016
  → T017 → T018 → 별도 구현 단계
```

스토리의 문서상 배치는 P1 세 스토리 후 P2 순서이며 ID 순서 자체를 실행 순서로 해석하지 않는다. 실행 순서는 계정 근거·비용 최종 판정을 설계보다 먼저 배치하고 상태/인증 설계를 연결 설계에 선행시킨다. T004에서 T003의 재개 근거와 모순된 비용 충돌을 확인하면 T009에서 차단으로 판정하고 이후 작업을 중단한다. T010·T012·T013 등에서 사용 자원이나 가정이 바뀌면 T009의 비용 판정을 재평가하고, 근거 부족·0원 초과 상태에서 설계를 계속하지 않는다.

## 병렬 실행 예시

현재 목록에서는 `[P]`를 부여하지 않았다. 연구·계획·quickstart를 여러 스토리가 공유하여 동시에 편집하면 충돌하고, 비용·저장·인증 결정이 연결 설계에 선행한다.

| 스토리 | 실행 예시 | 병렬 표시를 하지 않은 이유 |
|---|---|---|
| US1 | T006 → T007 → T008 | 확정된 인증·저장 정책이 필요하며 shared 문서 편집 |
| US2 | T009 → T010 → T011 | 계정 근거 → 제한 정책 → 검증 절차 순서 |
| US3 | T012 → T013 → T014 | 데이터/원자성 → 호출 계약 → 검증 준비 순서 |
| US4 | T015 → T016 | 복구 조건 확정 후 검증 절차 작성 |

향후 구현용 목록에서 파일 소유권과 의존성이 분리된 테스트/adapter 작업에만 병렬 표시를 검토한다. 이 문서는 에이전트 병렬 실행을 요청하지 않는다.

## 구현 전략과 MVP

현재 허용된 최소 산출물은 보류 상태와 인수인계 정보의 문서 정합성이다. 배포 MVP는 승인된 비용 조건 아래 US1의 연결을 먼저 증명하되 US2의 비용 게이트와 US3의 팀 인증·상태 보존을 필수 선행 조건으로 삼는다. 이 제약을 생략하여 US1만 배포하지 않는다.

이 목록은 설계 선행 작업 18개(준비2·기반3·US1 3·US2 3·US3 3·US4 2·공통2)다. 실제 코드 구현·원격 테스트·배포 작업을 모두 포함한 최종 목록은 T018에서 생성해야 한다. 모든 체크 완료가 명세의 운영 성공을 뜻하지 않는다.

## 실행 기록

- `setup-tasks.ps1 -Json`의 내용에 대해 메모리 내에서 feature 경로 해석에 `-NoPersist`를 추가하여 실행했다. helper 원본은 수정하지 않았으며 공용 feature pointer는 보존했다. 원본 helper의 자동 pointer 저장 부수 효과를 피하기 위한 실행상 조정이다.
- FEATURE_DIR는 `specs/005-cloud-run-deployment`와 일치했고 AVAILABLE_DOCS는 `research.md`였다. 추가 인수인계 근거로 `handoff.md`를 읽었다.
- 구성된 tasks template의 단계·체크리스트 형식을 사용했으며 실행 대상은 위 명시한 선행 문서 작업으로 제한했다.
- before/after tasks 확인 시 `.specify/extensions.yml`이 없으므로 extension hook을 실행하지 않았다.
- 이 명령은 작업 목록 생성만 수행했다. 위 체크리스트 작업, 코드 수정, 런타임 테스트, 계정 조회, 클라우드 변경, 배포, commit을 수행하지 않았다.
