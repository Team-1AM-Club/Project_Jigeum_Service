# Feature Specification: 공공데이터 교통 API 연동

**Feature Branch**: `feature/mcp-server-integrate` (현재 브랜치 유지; 새 브랜치 생성 없음)

**Created**: 2026-09-16

**Status**: Specified — 사용자 범위 확정, 계획 단계 준비 완료 (구현·실제 호출 미실행)

**Input**: User description: "이번 세션에서는 공공데이터 API 연동만 진행한다. 필요한 제공처의 API 키는 발급받았으며, 연동을 위한 spec부터 수립한다. 모호하거나 사용자 정보 제공이 필요한 사항은 질의한다. 사용자 허가 없이 commit하지 않는다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 확인된 제공처에서 실제 교통 데이터 조회 (Priority: P1)

사용자는 합의한 지역·교통수단·조회 기능에 대해 실제 공공데이터를 받으며, 어떤 기관의 어떤 시점 정보를 사용했는지 확인할 수 있다. 운영자는 이미 발급받은 자격증명을 실행 환경에 설정해 연동을 검증할 수 있다.

**Why this priority**: 현재 Mock 기반 교통 정보를 실제 조회로 연결하는 것이 이번 작업의 목적이다.

**Independent Test**: 합의한 서비스별로 지원되는 조회 조건과 기대 결과를 선정하고, 실제 조회 결과를 같은 조건의 제공처 응답과 대조한다. 아직 선정하지 않은 조회 기능은 구현 대상으로 간주하지 않는다.

**Acceptance Scenarios**:

1. **Given** 합의한 제공처의 유효한 자격증명과 지원되는 조회 조건이 있을 때, **When** 교통 정보를 조회하면, **Then** 제공처 응답에 근거한 결과와 출처·기준시각을 확인할 수 있다.
2. **Given** 제공처가 정상적으로 빈 결과를 반환할 때, **When** 조회 결과를 처리하면, **Then** 데이터 없음과 제공처 장애를 구분하고 가상 교통편을 생성하지 않는다.
3. **Given** 실제 정보를 사용하는 결과가 있을 때, **When** 기존 서비스 흐름으로 전달하면, **Then** 공동 계약에 맞게 실제/시연 여부와 출처를 보존한다. 합의하지 않은 공개 계약 변경은 하지 않는다.

---

### User Story 2 - 조회 실패와 미지원 범위를 정확하게 구분 (Priority: P1)

사용자는 지원되지 않는 조건이나 제공처 장애가 발생했을 때 성공한 교통 조회로 오해하지 않고, 재시도 또는 조건 변경이 필요한지 알 수 있다.

**Why this priority**: 제공처 장애나 데이터 부족이 잘못된 출발시각·막차 판단으로 이어지지 않아야 한다.

**Independent Test**: 자격증명 누락·거부, 호출 한도 초과, 응답 지연, 잘못된 응답, 정상 빈 결과, 미지원 조회를 각각 재현하고 결과의 의미를 비교한다.

**Acceptance Scenarios**:

1. **Given** 자격증명이 없거나 제공처가 인증을 거부할 때, **When** 조회하면, **Then** 실패를 명확하게 표시하고 응답·로그에 자격증명을 노출하지 않는다.
2. **Given** 호출 한도 초과·응답 지연·제공처 장애가 있을 때, **When** 조회하면, **Then** 제한된 시간과 호출 횟수 안에서 종료하고 실패를 Mock 결과로 자동 대체하지 않는다.
3. **Given** 지역·노선·방향·운행일 또는 조회 기능이 검증 범위 밖일 때, **When** 조회나 계산을 요청하면, **Then** 미지원 사유를 안내하고 검증되지 않은 경로·시간을 반환하지 않는다.
4. **Given** 실시간 도착 정보만 확보됐을 때, **When** 전체 경로·미래 시각·막차 환승의 근거로 사용하려 하면, **Then** 별도의 검증 근거가 없는 기능은 지원되는 것으로 표시하지 않는다.

### User Story 3 - 실제 연결 범위와 검증 증거 확인 (Priority: P2)

운영자와 공동 개발자는 어떤 조회가 실제로 성공했고 어떤 기능이 아직 미지원인지, 비밀 값이 없는 재현 절차로 확인할 수 있다.

**Why this priority**: 키 보유, 모의 검증 통과, 실제 조회 성공은 서로 다른 상태이므로 인수인계에서 구분해야 한다.

**Independent Test**: 서비스별 검증 기록의 조건·실행 시각·출처·성공/실패·제한사항과 실제 관측 결과를 대조한다.

**Acceptance Scenarios**:

1. **Given** 합의한 조회 기능을 실제로 실행했을 때, **When** 검증 결과를 기록하면, **Then** 비밀 값 없이 조회 조건·시각·출처·관측 결과·제한사항을 확인할 수 있다.
2. **Given** 기능의 데이터 근거가 부족하거나 실제 검증을 실행하지 못했을 때, **When** 지원 범위와 완료 상태를 설명하면, **Then** 미지원 또는 미검증 상태로 구분한다.

---

### User Story 4 - 실제 데이터로 약속 출발 계획 받기 (Priority: P1)

사용자는 서울 지하철·버스에 대해 출발지·목적지·도착 마감·도착 여유·허용 이동수단을 확인한 뒤, 검증된 실제 교통 데이터에 근거한 출발시각과 이동 후보를 받는다.

**Why this priority**: 조회 결과를 사용자의 이동 판단에 연결하는 것이 두 번째 단계의 완료 목표다.

**Independent Test**: 검증 범위 안에서 지하철·버스·지하철↔버스 혼합 환승 약속 사례를 각각 실행해 교통편·구간 연결·소요시간·목표 도착·권장 출발의 근거를 대조한다. 출발지·목적지는 역·정류소로 제한하며 혼합 환승에 필요한 보행 연결도 검증한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 이동 조건을 확인했고 필요한 경로·운행 근거가 모두 있을 때, **When** 약속 계획을 계산하면, **Then** 실제 이용 후보 1~3개와 권장 출발·예상 도착·근거·출처·기준시각을 기존 계약으로 받는다.
2. **Given** 도착 마감 19:00과 도착 여유 10분을 확인했을 때, **When** 계산하면, **Then** 목표 도착은 18:50이며 구간 또는 총 소요시간에 반영한 추가 여유를 다시 차감하지 않는다.
3. **Given** 경유 정류소나 역 목록은 있지만 운행 연결·소요시간을 검증할 근거가 없을 때, **When** 계획을 요청하면, **Then** 출발시각을 임의 계산하지 않고 데이터 부족 또는 미지원 사유를 안내한다.
4. **Given** 실제 이용 가능한 후보가 없거나 일부 정보만 조회됐을 때, **When** 결과를 받으면, **Then** 완전한 실제 경로의 성공 결과로 표시하지 않는다.
5. **Given** 역과 정류소 사이의 실제 보행 연결과 시간 근거가 있을 때, **When** 혼합 환승 계획을 계산하면, **Then** 보행·대기·이후 교통편 승차 가능성까지 검증한다. 직선거리만으로 연결 가능하다고 판단하지 않는다.
6. **Given** 주소·건물을 출발지 또는 목적지로 직접 요청할 때, **When** 계획 조건을 확인하면, **Then** 이번 범위에서 지원되는 역·정류소 선택을 요청하고 임의 주소의 도보 경로를 만들지 않는다.

---

### User Story 5 - 추가 운행 정보로 검증된 막차 계획 받기 (Priority: P2)

사용자는 지정한 서울 지하철·버스 운행일에서 목적지까지 연결 가능한 마지막 여정과 권장 출발시각을 확인한다. 마지막 열차 또는 버스 한 편이 존재한다는 사실만으로 목적지까지 도달 가능하다고 안내받지 않는다.

**Why this priority**: 막차 계획은 조회와 약속 계획에 이어, 운행일·방향·종착지·환승 연결을 검증한 후 완성해야 한다.

**Independent Test**: 지하철·버스·혼합 환승의 근거가 확보된 운행일별 막차 사례를 각각 실행하고, 가능한 연결·환승 불가·운행일 미지원·자정 이후 도착·권장 여유 부족을 비교한다.

**Acceptance Scenarios**:

1. **Given** 확인한 운행일과 각 구간의 운행·연결 근거가 있을 때, **When** 막차 계획을 요청하면, **Then** 실제 마지막 연결 여정의 이론상 최후 출발과 권장 출발을 구분하여 기존 계획 계약으로 반환한다.
2. **Given** 다음 날 00시 이후 운행이 요청 운행일에 속할 때, **When** 계산하면, **Then** 운행일과 실제 승하차 날짜를 구분하여 방향·종착지·환승 가능성을 검증한다.
3. **Given** 막차 데이터 미지원, 지원 범위 내 연결 가능한 여정 없음, 권장 여유 부족 중 하나일 때, **When** 결과를 처리하면, **Then** 기존 계약의 서로 다른 사유로 안내한다. 실시간 도착 또는 막차 여부 표시만으로 검증된 막차 여정을 만들지 않는다.
4. **Given** 최후 출발은 남았지만 권장 여유를 확보할 수 없을 때, **When** 계획을 요청하면, **Then** 가능한 경로로 강행 추천하지 않고 여유 미확보를 안내한다.
5. **Given** 한 교통수단의 막차는 남았지만 보행·대기 후 다른 교통수단에 승차할 수 없을 때, **When** 혼합 환승 막차를 평가하면, **Then** 목적지까지 연결 가능한 막차 여정으로 반환하지 않는다.

### Edge Cases

- 자격증명 미설정, 승인 대기, 권한 부족, 만료·거부.
- 정상 HTTP 응답 안에 제공처 오류 또는 호출 한도 초과가 포함되는 경우.
- 시간 초과, 연결 실패, 비정상 응답 형식, 필수 데이터 누락.
- 정상 빈 결과와 검색 식별자 오류·미지원 조건의 구분.
- 같은 역명·정류장명이 여러 노선·방향·운영기관에 존재하는 경우.
- 다음 날 시각으로 표시되는 자정 이후 운행, 평일·토요일·휴일과 실제 운행일의 구분.
- 조회 시각과 제공처 데이터 기준시각의 차이, 오래된 정보 또는 기준시각 미제공.
- 제공처 결과에 필요한 방향·종착역·환승·연결 근거가 없어 요청한 판단을 검증할 수 없는 경우.
- 결과가 여러 페이지에 나뉘어 일부만 조회된 경우; 부분 결과를 전체 데이터로 표시하지 않는다.
- 역과 정류소가 지도상 가까워도 출입구·횡단·통행 제한 때문에 실제 연결할 수 없거나 보행시간 근거가 없는 경우.
- 지하철과 버스의 마지막 운행이 각각 존재해도 환승 보행·대기 이후 다음 교통편을 탈 수 없는 경우.

## Requirements *(mandatory)*

### Confirmed Scope and Delivery Stages

- **기본 연동 대상**: 사용자 제공 목록의 지하철 도착정보·열차 위치·역 정보, 버스 정류소·노선·차량 위치 6개를 모두 포함한다.
- **지원 지역·교통수단**: 서울 지하철·버스. 이것은 모든 서울 노선·역·운행일을 즉시 지원한다는 의미가 아니며, 지원 판단은 실제 데이터 근거에 따른다.
- **계획 장소·환승 범위**: 출발지·목적지는 역·정류소 기준이며 동일 교통수단 내 환승과 지하철↔버스 혼합 환승을 포함한다. 혼합 환승을 위한 실제 보행 연결은 범위에 포함하고, 임의 주소·건물의 시작/종료 도보 연결은 포함하지 않는다.
- **추가 연동 대상**: 지하철 열차 시간표 OA-101·막차 시간표 OA-110·최단경로이동정보 서울 데이터 허브 100178와 버스도착정보 15000314. 사용자 진술상 이용 가능하며 실제 호출·필드·지원 범위는 검증한다.
- **단계 1**: 6개 서비스에 필요한 조회 기능을 연결하고 데이터를 정규화하며 실제 호출을 검증한다.
- **단계 2**: 필요한 운행·경로 데이터의 충분성을 검증한 후 기존 약속 계획을 실제 데이터에 연결한다.
- **단계 3**: 추가 시간표·막차 정보를 확보·검증하여 지하철·버스 막차 계획까지 연결한다.
- **전체 완료 조건**: 세 단계 모두 완료해야 한다. 단계 1의 성공만으로 이번 요청 전체를 완료 처리하지 않는다. 데이터 부족은 명시적 장애물로 기록하며 이후 단계의 성공으로 간주하지 않는다.

### Functional Requirements

- **FR-001**: 시스템은 공식 자료의 기본 6개 데이터셋을 모두 연동 대상으로 포함해야 한다. 필요한 상세조회 기능과 실제 승인·권한은 공식 문서 및 실행 환경에서 검증해야 하며, 모든 서비스의 모든 상세기능을 일괄 구현할 필요는 없다.
- **FR-002**: 이번 완료 범위는 조회·정규화·실제 호출 검증 → 약속 계획의 실제 데이터 연결 → 추가 시간표와 막차 계획 연결의 세 단계 모두다. 앞 단계의 검증 완료와 다음 단계에 필요한 데이터 확보를 확인하며 진행해야 한다.
- **FR-003**: 초기 지원 지역·교통수단은 서울 지하철·버스다. 서울 전체나 수도권 전체를 무조건 지원한다고 표시해서는 안 되며, 개별 요청의 지역·노선·방향·운행일을 확보한 데이터 범위와 대조해야 한다.

- **FR-008**: 자격증명은 백엔드 실행 환경에서만 관리해야 하며 저장소·설정 예제·도구 응답·로그·검증 기록에 실제 값을 포함해서는 안 된다. 키가 포함된 요청 주소와 제공처 오류 내용도 비밀 값을 제거해야 한다.
- **FR-009**: 데이터 없음, 미지원 조건, 자격증명 문제, 호출 한도 초과, 일시적 장애, 잘못된 응답을 구분하고 기존 공개 계약의 결과·오류 의미에 맞게 전달해야 한다.

- **FR-011**: 제공처별 역·정류장·노선·방향 식별자를 혼동하지 않아야 한다. 이름만으로 여러 후보 중 하나를 임의 확정해서는 안 된다.

- **FR-014**: 기존 공개 계약과 사용자 확인·후보 선택·계획 보호 규칙을 유지해야 한다. 공개 계약 변경이 필요한 경우 공동 합의와 API_SPEC.md·예제 JSON 갱신을 구현보다 먼저 수행해야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자 답변으로 합의한 조회 기능 100%에 대해 실제 성공 사례를 최소 1건씩 재현하고, 같은 조건의 제공처 응답과 결과의 의미가 일치함을 확인한다. 실행하지 못한 기능은 완료로 판정하지 않는다.
- **SC-002**: 실제 결과로 인정한 검증 사례 100%에서 출처와 데이터 기준시각을 확인할 수 있고, 실제/시연 표시가 관측 데이터와 일치한다.
- **SC-003**: 자격증명 문제·호출 한도 초과·응답 지연·잘못된 응답·정상 빈 결과·미지원 조건의 여섯 검증 분류 모두에서 성공 결과를 지어내거나 Mock으로 자동 전환하는 사례가 0건이다. 실패 재현은 비밀 값 없는 모의 응답으로 수행할 수 있다.
- **SC-004**: 검증한 요청·응답·로그·문서·설정 예제에서 실제 자격증명 노출이 0건이다.
- **SC-005**: 합의한 제공 서비스 100%에 대해 지원·미지원·미검증 항목과 비밀 값 없는 재현 절차를 기록한다. 운영자가 해당 절차로 실제 조회 결과 또는 명시적 실패를 확인할 수 있다.
- **SC-006**: 6개 기본 서비스 각각에서 최소 1개의 실제 조회와 정규화 결과를 대조하고, 필요한 원본 의미·단위·식별자·출처의 오변환이 0건임을 확인한다.
- **SC-007**: 검증 범위 내 지하철·버스 약속 사례를 각각 최소 1건 실행하여 사용자 조건 확인부터 실제 데이터 기반 후보 반환까지 재현한다. 모든 반환 구간의 운행·연결·시간 근거를 확인하고 도착 여유·추가 여유 중복 적용은 0건이다.
- **SC-008**: 검증 범위 내 지하철·버스 막차 사례를 각각 최소 1건 실행하여 운행일·방향·종착지·마지막 연결 여정·최후 출발·권장 출발의 근거를 대조한다. 자정 이후 도착, 연결 불가, 미지원 운행일, 권장 여유 부족의 네 경계 분류 모두에서 잘못된 성공 안내가 0건이다.
- **SC-009**: 지하철→버스와 버스→지하철 두 방향에서 약속·막차 사례를 각각 최소 1건씩 실행하여 실제 보행 연결과 각 교통편 승하차 가능성을 대조한다. 연결 불가 또는 시간 근거 부족 사례에서 잘못된 성공 안내는 0건이어야 한다. 주소·건물 기반 계획은 역·정류소 선택이 필요하다고 안내한다.
- **SC-010**: 외부 조회의 각 시도는 30초 상한 안에서 종료하고, 허용 오류의 자동 재시도는 500ms 대기 후 최대 1회, 금지 오류는 0회임을 재현 가능한 실패 검증으로 확인한다.

## Assumptions

- 사용자는 필요한 제공처의 API 키를 발급받았다. 개별 서비스의 승인·권한·정상 호출 여부는 아직 확인하지 않았다.
- 사용자가 제시한 공식 URL에서 제공기관과 서비스명을 확인했으며, 사용자는 6개 모두를 대상으로 확정했다. 개별 API 실제 호출 성공·정상 자격증명 검증을 실행했다는 의미는 아니다.
- 이번 단계는 명세 작성이며, 실제 자격증명 읽기·외부 조회·구현·배포를 실행하지 않는다.
- 제품 방향은 IDEA.md, 공개 계약은 API_SPEC.md, 제약은 프로젝트 헌법을 따른다. 사용자가 지원 대상을 서울 지하철·버스로 확정했으며, 세부 지원 노선·방향·운행일은 실제 데이터 검증 결과에 따른다.
- 실제 조회가 불가능한 기능은 미지원 또는 미검증으로 남긴다. 발급받은 서비스가 필요한 데이터에 충분한지 공식 문서 확인 전에는 가정하지 않는다.
- 실제 조회가 불가능하다는 이유로 사용자 요청 범위를 축소해 완료 처리하지 않는다. 필요한 연결·시간 근거의 확보가 막히면 장애물과 미완료 단계를 명시한다.
- MCP 서버·Hermes 모델·서비스 Agent·독립 클라이언트·회원가입·영구 이동 이력·알림·자동 재탐색·택시 최적화·인프라 변경은 이번 연동의 추가 개발 범위에 포함하지 않는다.
- 기존 작업 파일은 보존하며, 별도 명시적 허가 없이 commit하지 않는다.

#### Session 2026-09-16

- Q: 기본 데이터셋·완료 범위·지역은? → A: 6개 모두, 조회·정규화·실제 호출 검증부터 약속 계획과 추가 시간표·막차 계획까지 단계적으로 연결하며, 서울 지하철·버스를 지원한다.
- Q: 추가 시간표·막차·최단경로·버스 도착 서비스 이용 가능 여부는? → A: 가능. 실제 자격증명이나 호출 성공은 이번 명세 작성에서 확인하지 않았다.
- Q: 장소·환승 범위는? → A: 역·정류소 기준, 지하철↔버스 혼합 환승 포함.
- Q: 제공처 기준시각을 공개 계약에 어떻게 표현할 것인가? → A: Source.basis_at(datetime 또는 null) 변경안 작성을 승인했다. 실제 반영은 공동 개발자 합의 후 진행한다.
- Q: 초기 Safety Buffer 배정은? → A: 첫 승차 전 5분, 여정당 한 번. 실제 보행/대기와 구분하고 구간·총 소요에 한 번만 포함한다.
- Q: 별도 버스 운행표/구간 시간 및 환승 보행 자료를 확보했는가? → A: 없음, 추가 자료 조사 필요. 자료 결손은 구현 의존성으로 남기며 범위를 축소해 완료하지 않는다.
- Q: 최단경로 실제 서비스는? → A: 사용자가 100178의 실제 페이지를 OA-22724로 정정했다. API 대상은 OA-22724/getShtrmPath이며 15143842로 자동 대체하지 않는다.
