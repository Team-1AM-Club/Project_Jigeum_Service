# 003 분석 상위 4건 수정 제안

작성일: 2026-09-16  
상태: 사용자 요청으로 003 문서에 반영 — 공통 계약 합의·구현·실행 인수 전  
대상: [spec.md](spec.md), [plan.md](plan.md), [tasks.md](tasks.md)  
작성·검토 환경: Hermes/Solar Pro4

최초 요청은 기존 003 분석 결과의 구체적인 수정안 제안이었다. 이후 사용자가 `speckit-plan`·`speckit-tasks`와 003 관련 문서까지 동기화하도록 요청해 아래 수정 방향을 반영했다. 공통 API·공통 예제는 공동 합의 작업으로 남기며 MCP 진단 필드·REQUEST_TIMEOUT은 T001 전까지 미확정 권장안이다. 아래는 제안 당시 근거와 대체 문구를 보존한 기록이며 현재 반영본은 각 대상 문서를 따른다. 새 기능 번호·활성 004 설정·코드는 변경하지 않는다.

## U1 — 잘못된 응답에서도 적용 불명 상태 보존

근거: [MCP 계약](contracts/mcp-contract.md) §5~6, [HTTP 계약](contracts/http-contract.md) §4, `spec.md` US3 시나리오 4 및 FR-013~FR-017.

### 명세 대체·추가 문구

US3 시나리오 4를 다음과 같이 대체한다. 기존의 일괄적인 “기존 선택 유지”는 select가 이미 적용됐을 가능성을 놓치므로 수정한다.

> **Given** 검증 실패·충돌·만료 또는 재시도 불가 응답이 발생했을 때, **When** 응답을 처리하면, **Then** 자동 재시도하지 않는다. 신뢰할 수 있는 응답으로 미적용이 확정되면 기존 상태를 유지한다. 응답이 잘못되어 적용 여부를 확인할 수 없으면 성공·미적용·원상복구를 단정하지 않고 결과 미확정으로 안내한다.

US3에 시나리오 6을 추가한다.

> **Given** 서버가 상태 변경을 완료했으나 최초 응답이 깨지거나 요청과의 대응을 검증할 수 없을 때, **When** 사용자가 결과를 확인하면, **Then** 자동 재전송은 0회이며 원래 요청을 보존하고 새로운 상태 변경을 차단한다. 사용자가 명시적으로 복구를 요청하면 원래 요청으로 결과를 재수신하고 성공한 논리 동작의 상태 적용 횟수는 1회다.

FR-013에 다음 문장을 추가한다.

> 전송한 상태 변경의 적용 여부가 불명확하면 자동 재시도 허용 여부와 관계없이 원래 요청을 보존하고 새로운 상태 변경을 차단해야 한다. 사용자가 명시적으로 복구를 요청한 경우에만 동일 요청을 재전송하며, 확정된 응답 또는 계약상 종료 사유를 확보하기 전에는 미적용으로 처리하지 않아야 한다.

SC-003에 잘못된 최초 성공 응답 사례를 추가한다. 성공이 확인된 논리 동작은 적용 1회, 확정된 미적용 실패는 적용 0회로 검증한다.

### 계약 판정표

| 수신 상황                                                 | 자동 추가 시도               | MCP 처리                                                                     |
| --------------------------------------------------------- | ---------------------------- | ---------------------------------------------------------------------------- |
| 신뢰할 수 있는 성공 응답                                  | 없음                         | 성공 처리 또는 동일 키 replay. 관측 최대 revision을 낮추지 않음              |
| 유효하고 요청 대응이 확인되며 미적용을 보장하는 최종 오류 | FR-015의 허용 조건에서만 1회 | 허용 시 500ms 뒤 동일 요청. 최종 미적용 확정이면 보류 해제                   |
| 전송 이후 연결 유실·timeout으로 적용 여부 불명            | 남은 허용 예산 내 최대 1회   | 추가 시도 후에도 미확정이면 OUTCOME_UNKNOWN                                  |
| POST 응답의 JSON/schema/헤더 키/status 조합 불일치        | 0회                          | 첫 시도 직후에도 OUTCOME_UNKNOWN, 원인 분류는 UPSTREAM_RESPONSE_INVALID      |
| GET 응답의 JSON/schema/헤더/status 불일치                 | 0회                          | UPSTREAM_RESPONSE_INVALID. 조회 실패만으로 상태 변경 보류를 새로 만들지 않음 |

`mcp-contract.md`의 “두 번의 허용 HTTP 시도에서도” 문구를 다음으로 대체한다.

> POST 전송 후 서버 적용 여부를 확정할 수 없고 더 이상의 자동 시도가 허용되지 않으면, 현재 시도 횟수와 관계없이 OUTCOME_UNKNOWN으로 보류한다. 잘못된 응답이면 첫 시도에서도 보류한다. 새로운 상태 변경은 REQUEST_PENDING으로 차단하고 GET 조회만 허용한다. 원래 단계·키·직렬화 body·revision·시각 값과 남은 자동 재시도 예산을 유지한다.

도구의 대표 오류는 OUTCOME_UNKNOWN으로 전달하고, 원인 분류 UPSTREAM_RESPONSE_INVALID는 안전한 진단 정보로 구분한다. 정확한 진단 필드명은 T001에서 기존 MCP 오류 구조와 함께 합의하며 서버 envelope의 error.code는 바꾸지 않는다.

`resume`은 실제 elicitation 승인을 받은 뒤 원래 POST를 1회 전송한다. 자동 재시도 예산을 초기화하지 않는다. 다시 잘못된 응답이면 보류를 유지한다. GET의 revision 변화만으로 해당 요청의 성공·실패를 확정하지 않는다. 유효하고 요청 대응이 확인된 성공 replay, 미적용이 보장된 최종 오류, 계약상 대화 만료 등 종료 사유를 구별한다. 만료는 과거 미적용의 증거가 아니며 과거 결과를 복원하지 않는다.

서버가 유효 envelope로 반환한 UPSTREAM_RESPONSE_INVALID와 MCP가 깨진 HTTP 응답을 보고 만든 같은 이름의 진단은 구분한다. 전자는 계약상 미적용이 보장될 때만 확정 실패이고, 후자는 적용 불명이다. 프로세스 종료 후 복구 보장은 추가하지 않는다.

### 작업·검증 보강

- T035: 서버 commit 후 JSON 파손/schema 누락/키 불일치/status 불일치를 각각 주입한다. 자동 추가 시도 0회와 첫 응답 직후 보류를 검증한다.
- T038: 미확정 보류와 오류 원인 분리, GET 허용·새 변경 차단·동일 키 resume을 구현 대상으로 명시한다.
- T040: GET으로 최신 revision을 관측한 뒤 오래된 replay를 받아도 상태를 되돌리지 않는 사례를 유지한다.
- T041: confirm/plan/select 각 단계에서 최초 파손 응답→보류→명시적 resume→성공 replay를 검증한다. replan은 T048에서 같은 회귀 사례를 추가한다.
- `contracts/examples.json`에는 MCP 전송 장애 시나리오와 백엔드의 유효 오류 fixture를 구별해 추가하고, `quickstart.md` V04·V05·V06·V11에 실행 증거를 연결한다.

## G1 — 서버 처리 제한의 담당·경계 검증 명시

근거: [API_SPEC.md](../../API_SPEC.md) §12, `plan.md`의 시간 제한, T039의 MCP 대기 제한. 서버 timeout 미구현을 단정하는 지적이 아니라 작업 목록의 검증 책임 공백이다.

### 명세 보강 문구

FR-016에 다음 문장을 추가한다.

> 처리 제한시간 안에 확정하지 못한 계산의 늦은 결과는 이후 상태에 적용하지 않아야 한다. 제한시간 전에 이미 확정된 변경의 응답이 늦거나 유실된 경우에는 이를 원상복구 또는 미적용으로 안내하지 않고 동일 요청 복구 규칙을 적용해야 한다.

SC-008에 제한시간 경계 증거를 포함한다. 사용자 관점의 명세에는 특정 테스트 라이브러리나 구현 구조를 넣지 않고 아래 수치는 계획·HTTP 계약에 둔다.

### 시간 및 오류 계약 제안

| 대상                  | 서버 처리 예산 | 담당                                              |
| --------------------- | -------------- | ------------------------------------------------- |
| health/capabilities   | 3초            | 백엔드 담당                                       |
| places                | 10초           | 백엔드 담당                                       |
| interpret/plan/replan | 25초           | 백엔드 담당, provider 내부 예산은 004 담당과 조율 |

측정은 서버의 해당 핸들러 진입부터 결과 검증·상태 확정까지의 경과시간으로 정의하고, 단조 시계를 사용한다. 네트워크 전달 시간과 사용자 elicitation 대기는 포함하지 않는다. 제공처별 호출이 각각 전체 예산을 새로 받지 않도록 남은 예산 안에서 실행한다. 새 상태 조회·확인·선택 경로의 별도 SLA는 이번 결함 수정에서 임의로 추가하지 않는다.

원자적 상태 확정 지점에서 경과시간이 제한 이상이면 그 요청의 새로운 상태 변경을 거부한다. 응답을 timeout으로 바꾼 뒤 작업이 뒤늦게 commit하는 구현은 허용하지 않는다. 이미 제한 안에서 commit한 요청의 응답 전달이 늦은 경우에는 성공 기록을 보존하고 replay로 회수한다. 취소만으로 commit 방지가 보장됐다고 판단하지 않는다.

오류 매핑 권장안은 다음과 같으며 T001 공동 계약 검토 대상이다.

- 외부 요청 timeout은 기존 `504 / error / UPSTREAM_TIMEOUT`을 유지한다.
- 서버 자체의 전체 처리 예산 소진은 `504 / error / REQUEST_TIMEOUT`, `retryable=true`를 제안한다. 미적용을 보장한 경우에만 이 확정 오류를 반환한다. 새 코드는 공동 합의 후 오류표와 예제에 함께 추가한다.
- MCP가 유효 오류를 받으면 기존 FR-015에 따라 500ms 뒤 같은 키·본문으로 최대 1회 자동 추가 시도한다. 응답 자체가 유실되면 U1의 적용 불명 절차를 따른다. 백엔드 workflow의 자동 재시도는 추가하지 않는다.

### 새 작업 제안

**T064 [US3] — 서버 처리 제한 적용·경계 검증**

백엔드 담당이 T004에서 확인한 기존 timeout 처리 위치·서비스·테스트를 먼저 조사하고 경로를 `quickstart.md`에 기록한다. 기존 처리가 조건을 만족하면 재사용하며, 부족한 처리만 수정한다. T010의 원자적 상태 확정 규칙과 연결하고 004 제공처 담당과 중첩 호출 예산을 확인한다. T034~T040과 함께 US3에서 수행하고 T041의 선행 작업으로 둔다.

검증 범위는 3초·10초·25초 각각의 직전·정확한 경계·초과, provider 지연, 늦은 성공 도착, 이미 commit한 응답의 지연이다. 시간 제어가 가능한 테스트를 사용하고 단순 실시간 sleep 결과만으로 판정하지 않는다.

미확정 timeout 사례에서 confirmed_trip·후보·기존 선택·revision·updated_at·TTL 갱신 0회, 후속 늦은 결과 적용 0회를 확인한다. 독립적인 자연 만료 처리는 구분하며 실패 때문에 수명이 연장되지 않아야 한다. confirm 성공 후 plan timeout이면 plan 직전 상태를 기준으로 비교하여 앞선 confirm 성공을 되돌리지 않는다. 이미 commit한 응답 지연은 최초 성공 기록 유지와 상태 중복 적용 0회를 검증한다.

영향 문서는 `plan.md`, `contracts/http-contract.md`, `tasks.md`, `quickstart.md`다. 새 오류를 채택하면 T002에서 `API_SPEC.md`와 `Docs/api/examples.json`을 함께 갱신한다. 연결되는 호출처·오류 분기·fixture·테스트를 T059에서 확인한다. 제공처 신규 구현은 004 범위로 유지한다.

## 반영 순서와 검토 결과

1. C1의 판정 분리와 출처 보존 문구를 반영한다. 미충족 조건을 통과로 바꾸지 않는다.
2. U1·G1의 명세 문구와 C2의 인수 순서를 003 내에서 동기화한다.
3. T062·T063·T064를 추가하고 T055·T056의 범위, T041 선행 조건, 전체 의존성·FR/SC 추적표를 갱신한다. 채택 시 작업 수는 61개에서 64개가 된다.
4. 공동 검토 T001에서 MCP 오류 진단 표현과 서버 REQUEST_TIMEOUT 제안을 포함한 공개 계약을 확정한 뒤 T002를 수행한다.
5. 문서 정합성을 다시 분석한다. 실제 MCP 경로·환경·제공처 등 구현 선행 조건은 별도로 충족해야 한다.

최초 검토 결과: 네 결함마다 대상 문구, 변경 위치, 담당 작업, 측정 가능한 인수 기준을 제시했다. 새 제품 기능·계정·저장 인프라·원격 배포를 추가하지 않는다. 후속 사용자 승인은 003 문서 반영 범위이며 공동 API 합의·구현 승인과 구별한다.

최초 제안 단계의 산출물은 이 제안서 하나였다. 후속 반영 단계에서는 003 spec·plan·tasks·계약·검증 안내를 동기화했다. 런타임 테스트·실제 사용자 승인·제공처 호출은 수행하지 않았다. 남은 단계는 T001 공동 검토, T002 공통 계약 동기화와 실제 구현 선행 조건 해소다.
