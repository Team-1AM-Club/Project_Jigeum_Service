**Feature Branch**: `feature/mcp-server-integrate` (현재 브랜치 유지)

**Created**: 2026-09-16

**Status**: Draft — 요구사항 검토 완료, 공동 계약 상세화·실제 연동 검증 전

**Input**: User description: "Docs/mcp-http-integration.md와 첨부한 MCP HTTP 연결 현황 이미지를 대조해 통합 명세를 작성한다. 서버 대화 상태와 확인·선택·revision 전달 계약을 이번 통합에 포함한다. 제한된 오류에는 500ms 후 최대 1회, 동일 키·본문으로 재시도한다."

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 같은 조건과 결과로 약속 계획 받기 (Priority: P1)

사용자는 지원 범위를 확인하고 장소를 선택한 뒤, 자연어로 전달한 약속 조건을 확인하여 출발시각과 경로 후보를 받는다. 담당자가 다른 구성 요소를 연결해도 입력·질문·결과의 의미가 바뀌지 않아야 한다.

**Why this priority**: 현재 보고된 입력·응답 형식 차이는 약속 계획의 기본 흐름 자체를 막는다.

**Independent Test**: 지원 범위 조회 → 장소 검색 → 입력 해석 → 조건 확인 → 약속 계획을 실행하고, 각 단계에서 전달한 조건과 받은 결과를 공동 계약과 대조한다.

**Acceptance Scenarios**:

1. **Given** 검증 가능한 장소와 서비스 지원 범위가 있을 때, **When** 다섯 사용자 작업 중 조회·해석·계획 작업을 수행하면, **Then** 같은 공개 계약으로 연결되며 다른 형식을 정상 결과처럼 임의 변환하지 않는다.
2. **Given** 사용자가 19:00 도착과 10분의 도착 여유를 명확히 지정했을 때, **When** 해석하고 최종 확인 후 계산하면, **Then** 목표 도착은 18:50이며 이미 명확한 마감시각을 다시 묻지 않는다. 부족한 정보는 한 번에 최대 3개 질문으로 확인한다.
3. **Given** 이용 가능한 후보가 있을 때, **When** 결과를 받으면, **Then** 후보 1~3개, 권장 출발·예상 도착시각, 경로, 여유의 근거, 출처·기준시각을 확인할 수 있고 여유시간을 중복 적용하지 않는다.
4. **Given** 입력 부족·지원 불가·경로 없음·제공처 장애 중 하나가 발생했을 때, **When** 결과를 안내하면, **Then** 성공과 구별된 사유 및 가능한 다음 행동을 제공하며 성공 계획을 만들어 보충하지 않는다.

### User Story 2 - 확인한 조건만 현재 대화에서 계산하기 (Priority: P1)

사용자는 본인이 확인한 장소·날짜·시각·이동수단에 대해서만 계산되기를 원한다. 서버는 대화의 확인 조건·후보·선택 계획을 기준 상태로 관리하고, 오래된 요청이나 다른 대화가 이를 바꾸지 못하게 한다.

**Why this priority**: 단순 확인 플래그나 입력 준비 완료만으로는 실제 사용자 동의 및 최신 조건을 보장하지 못한다.

**Independent Test**: 대화 생성, 조건 확인, 조건 변경, 오래된 버전 요청, 다른 대화의 상태 사용, 만료를 각각 재현하여 계산 실행 여부와 상태 변화를 검사한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 조건 요약을 확인하지 않았을 때, **When** 입력 준비 완료 또는 모델이 생성한 확인 값만으로 계산을 요청하면, **Then** 계산을 거부하고 실제 확인에 필요한 정보를 안내한다.
2. **Given** 사용자가 조건 A를 확인했을 때, **When** 장소·날짜·시각·여유·이동수단 중 하나를 B로 변경하면, **Then** A의 확인은 B에 재사용되지 않으며 B를 다시 확인해야 계산할 수 있다.
3. **Given** 같은 대화의 상태가 갱신됐을 때, **When** 오래된 상태 버전으로 새 변경을 요청하면, **Then** 충돌을 알리고 최신 상태를 기준으로 다시 확인하도록 하며 뒤늦은 결과로 최신 상태를 덮어쓰지 않는다.
4. **Given** 두 대화가 서로 다른 조건을 가질 때, **When** 한 대화의 확인·후보·선택을 다른 대화에 사용하면, **Then** 상태 혼용을 거부한다.
5. **Given** 대화가 만료됐거나 존재하지 않을 때, **When** 과거 확인을 사용하면, **Then** 정해진 만료·미존재 결과로 거부한다. 대화는 유효하고 후보만 만료됐으면 확인 조건과 기존 선택은 유지하고 새 후보 조회를 안내한다.

### User Story 3 - 요청을 재전송해도 중복 적용하지 않기 (Priority: P1)

사용자는 일시적인 연결 문제에서 제한된 재시도를 받을 수 있다. 동일한 동작이 중복 적용되거나 오류가 무제한 호출로 이어져서는 안 된다.

**Why this priority**: 멱등성 키를 보내는 것과 서버가 중복 적용을 막는 것은 별도 검증 대상이다.

**Independent Test**: 최초 응답 유실, 같은 요청 재전송, 같은 키의 다른 요청, 재시도 불가 오류를 재현하여 호출 횟수·결과·상태 변경 횟수를 비교한다.

**Acceptance Scenarios**:

1. **Given** 성공한 논리 요청이 있고 대화가 유효할 때, **When** 같은 키와 같은 요청을 다시 보내면, **Then** 최초 결과를 재생하고 상태를 두 번 변경하지 않는다. 이미 처리된 요청의 재생은 오래된 버전 충돌보다 우선한다.
2. **Given** 동일 키가 이미 사용됐을 때, **When** 조건·작업 종류·대상 등 의미가 다른 요청에 재사용하면, **Then** 충돌을 반환하고 이전 결과를 새 요청의 성공으로 제시하지 않는다.
3. **Given** 허용된 일시적 연결·시간 초과·재시도 가능 장애가 발생했을 때, **When** 자동 복구를 시도하면, **Then** 500ms 대기 후 최대 1회만 동일 요청으로 재시도한다. 다시 실패하면 결과 미수신 또는 오류를 안내한다.
4. **Given** 검증 실패·상태 충돌·만료·잘못된 응답 또는 재시도 불가 오류일 때, **When** 결과를 처리하면, **Then** 자동 재시도하지 않는다. 요청에 대응하는 유효한 최종 오류로 미적용이 확인되면 기존 상태를 유지한다. 전송 후 응답이 깨져 적용 여부를 모르면 성공·미적용·원상복구를 단정하지 않고 결과를 보류한다.
5. **Given** 새 대화의 최초 성공 응답이 유실됐거나 기존 대화가 이미 만료됐을 때, **When** 같은 요청을 재전송하면, **Then** 최초 요청 중복으로 새 대화를 여러 개 만들지 않고, 만료된 대화의 과거 성공 결과도 복원하지 않는다.
6. **Given** 서버가 변경을 확정했지만 최초 응답의 형식 또는 요청 대응 정보가 깨졌을 때, **When** 연동 계층이 이를 받으면, **Then** 자동 추가 시도는 0회이고 원래 요청을 보존한 채 새 변경을 차단한다. 사용자의 명시적 복구로 최초 성공을 재생해도 상태 적용은 총 1회다.

### User Story 4 - 재탐색 후보를 비교하고 직접 선택하기 (Priority: P2)

사용자는 버스·환승을 놓치면 현재 출발 기준점에서 다시 계산하고, 기존 선택과 비교한 뒤 새 후보를 직접 선택한다.

**Why this priority**: 재탐색 조회와 선택 적용을 분리해야 사용자의 계획 통제권이 유지된다.

**Independent Test**: 기존 선택을 가진 대화에서 재탐색 성공·다른 후보 선택·취소·실패·후보 만료를 각각 실행하고 서버의 선택 상태를 비교한다.

**Acceptance Scenarios**:

1. **Given** 기존 선택 계획이 있을 때, **When** 사용자가 현재 출발지와 유지할 목적지·마감 조건을 확인하고 재탐색하면, **Then** 새 출발지의 후보와 기존 선택 대비 변화를 제공하되 기존 선택은 유지한다.
2. **Given** 이전 도착이 18:50이고 새 권장 후보 도착이 19:10일 때, **When** 비교 결과를 설명하면, **Then** 20분 늦어짐으로 설명한다. 마감 19:00에 대한 지각 10분과 도착 여유 부족을 구분한다.
3. **Given** 새 후보 중 하나를 사용자가 명시적으로 선택했을 때, **When** 선택이 유효하게 적용되면, **Then** 서버의 현재 선택과 상태 버전이 함께 갱신된다. 권장 후보와 다른 후보를 선택하면 권장 후보 전용 비교 설명을 그대로 쓰지 않는다.
4. **Given** 재탐색 실패·취소·만료된 후보 선택이 발생했을 때, **When** 결과를 처리하면, **Then** 기존 선택을 삭제하거나 자동 교체하지 않는다. 기존 경로의 현재 이용 가능성을 보장한다고 설명하지 않는다.

### User Story 5 - 검증된 막차와 실제 연결 범위 확인하기 (Priority: P2)

사용자는 약속 계획과 같은 계획 기능으로 막차 귀가를 요청하고, 실제 데이터인지 시연 자료인지 구별할 수 있다. 두 개발자는 재현 가능한 자료로 연결 상태를 인수한다.

**Why this priority**: 모의 서버 통과가 실제 교통 조회나 실제 대화 시연 성공으로 잘못 전달되는 것을 막는다.

**Independent Test**: 지원되는 막차, 미지원 운행일, 경로 없음, 실제 데이터 조회 실패를 실행한다. 별도로 실제 백엔드 연결과 지정된 대화 환경의 도구 호출 기록을 확인한다.

**Acceptance Scenarios**:

1. **Given** 검증된 노선·운행일 데이터가 있을 때, **When** 막차 계획을 요청하면, **Then** 일반 계획 작업에서 막차 유형으로 처리하고 운행일과 다음 날 도착을 구별하며 이론상 최후 출발과 권장 출발을 함께 설명한다.
2. **Given** 막차 데이터 미지원·검증 범위 내 경로 없음·권장 여유 미확보 중 하나일 때, **When** 계산하면, **Then** 각각의 사유를 구분하고 검증하지 못한 경로나 출발시각을 만들지 않는다.
3. **Given** 실제 데이터 조회가 실패하거나 잘못된 응답이 왔을 때, **When** 결과를 처리하면, **Then** 데모로 자동 전환하거나 원본 오류 페이지를 노출하지 않는다. 실제 연결 방식과 결과 데이터의 데모 여부는 별도로 식별한다.
4. **Given** 통합 인수 자료를 준비할 때, **When** 완료 여부를 판단하면, **Then** 수정 버전·실행 주소·실제 요청/응답·확인 거부·재생/충돌 결과·대화 도구 호출 증거를 구분해 제시하며 미실행 검증은 미실행으로 남긴다. 기록의 도구·모델은 실제 사용 내역과 일치하고 비밀키·불필요한 개인정보를 포함하지 않는다.

### Edge Cases

- 자연어와 장소 검색어의 공백·한글·특수문자가 전달 중 훼손되거나, 출발·도착 장소가 확정되지 않은 경우.
- 해석은 준비됐지만 사용자 확인이 없거나, 확인 직후 조건이 변경된 경우.
- 첫 대화 생성 응답이 유실되어 서버 식별자를 아직 받지 못한 상태에서 같은 요청을 재전송하는 경우.
- 동일 키의 동시 요청, 다른 작업·본문으로의 키 재사용, 성공 후 오래된 버전 재생이 겹치는 경우.
- 외부 조회 중 상태 버전이 변경되거나 대화가 만료되는 경우. 뒤늦은 결과를 적용하지 않는다.
- 후보만 만료된 경우와 대화 전체 만료, 존재하지 않는 대화를 혼동하는 경우.
- 해석 가능한 업무상 이용 불가 결과, 비정상 전송 상태의 계약 응답, 형식이 깨진 응답이 각각 도착하는 경우.
- 서버가 변경을 확정한 뒤 첫 응답만 깨진 경우. 자동 재시도 금지와 서버 미적용을 동일하게 판단하지 않는다.
- 처리 제한 경계에서 계산 결과가 도착하거나 확정된 성공 응답의 전달만 지연되는 경우. 미확정 결과의 늦은 적용 차단과 이미 확정된 성공의 복구를 구별한다.
- 실제 서버가 데모 데이터를 반환하는 경우. 서버 연결 성공은 실데이터 검증 성공과 다르다.
- 막차 운행일과 자정 이후 실제 승하차 날짜가 다르거나 권장 출발시각이 이미 지난 경우.
- 새 후보가 도착하기 전에 조건이 변경되거나, 사용자가 비교 대상이 아닌 후보를 선택한 경우.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 지원 범위 조회·장소 검색·조건 해석·약속/막차 계획·재탐색의 다섯 사용자 작업은 양쪽 담당자가 합의한 하나의 공개 계약으로 연결되어야 한다. 확인·선택은 이 작업 흐름 안에서 제공하며 별도 제품 기능으로 범위를 늘리지 않는다.
- **FR-002**: 입력과 결과의 구조·필수 여부·상태·오류 의미가 다르면 이를 계약 불일치로 식별해야 한다. 실제 백엔드 형식을 추측해 누락 정보를 생성하거나 호환되는 것처럼 숨기지 않아야 한다.

- **FR-004**: 계산 전 최종 조건 요약과 실제 사용자 확인을 결부해야 한다. 입력 준비 완료나 모델이 생성한 확인 값만으로 계산을 허용하지 않아야 하며, 조건 변경 시 재확인이 필요하다.
- **FR-005**: 서버는 대화 식별자·상태 버전·만료시각 및 확인 조건·후보·선택 계획의 기준 상태를 관리해야 한다. 대화 간 상태를 혼용하거나 연동 계층의 자유 서술로 서버 상태를 덮어쓰지 않아야 한다.
- **FR-006**: 최초 대화 식별자는 서버가 발급하고, 후속 상태 변경은 해당 대화와 마지막으로 받은 상태 버전에 결부해야 한다. 유효한 상태 변경 성공만 버전을 증가시키며 상태 충돌과 만료를 거부해야 한다.

- **FR-008**: 계획 결과는 후보 1~3개, 권장 출발·예상 도착, 경로·여유 근거, 출처·기준시각을 제공해야 한다. 연결·설명 과정에서 시간을 재계산하여 여유를 중복 적용하지 않아야 한다.
- **FR-009**: 약속과 막차는 하나의 계획 작업에서 유형으로 구분해야 한다. 막차는 검증된 범위에서만 제공하고 미지원·경로 없음·권장 여유 미확보를 구별해야 한다.
- **FR-010**: 재탐색은 사용자의 요청과 확인된 현재 출발 기준점으로 수행해야 한다. 유지할 목적지·마감·선호 및 이전 선택의 비교 기준을 일관되게 전달해야 한다.
- **FR-011**: 새 후보 생성은 기존 선택을 바꾸지 않아야 한다. 사용자가 유효한 후보를 명시적으로 선택한 뒤 서버의 선택 상태와 버전을 갱신해야 한다.
- **FR-012**: 재탐색 실패·취소·미선택·만료 후보는 기존 선택을 삭제하지 않아야 한다. 비교는 명시된 대상 후보에만 적용하고, 지각과 도착 여유 부족을 구별해야 한다.
- **FR-013**: 연동 계층은 논리적 상태 변경마다 중복 방지 키를 관리해야 한다. 동일 요청의 재전송은 최초 키·본문·상태 버전을 유지하고, 다른 논리 동작은 새 키를 사용해야 한다. 사용자나 모델에게 키 생성·관리를 맡기지 않아야 한다. 전송 후 적용 여부가 불명확하면 시도 횟수와 관계없이 원래 요청·시각·남은 재시도 예산을 보존하고 새 상태 변경을 차단해야 한다. 자동 재시도 금지 오류도 적용 여부와 별도로 판정하며, 명시적 복구는 원래 요청만 재전송해야 한다. 최신 상태 조회만으로 그 요청의 성공을 단정하지 않아야 한다.
- **FR-014**: 서버는 유효한 대화에서 동일 키·동일 요청의 성공 결과를 재생하고 중복 적용하지 않아야 한다. 다른 요청으로 키를 재사용하면 충돌로 거부해야 한다. 최초 대화 생성 응답 유실도 중복 생성 없이 처리해야 한다.
- **FR-015**: 자동 재시도는 연결 실패·시간 초과 또는 계약상 재시도 가능한 일시 장애에만 500ms 후 최대 1회 허용해야 한다. 재시도 불가 응답, 검증 실패·충돌·만료·잘못된 응답은 자동 재시도하지 않아야 한다.
- **FR-016**: 조회 실패나 조회 중 발생한 상태 충돌·만료는 확인 조건·후보·선택 및 수명을 성공한 변경처럼 갱신하지 않아야 한다. 늦게 도착한 결과도 최신 상태를 덮어쓰지 않아야 한다. 처리 제한시간 안에 확정하지 못한 계산의 늦은 결과는 이후 상태에 적용하지 않아야 한다. 제한시간 전에 이미 확정된 변경의 응답이 늦거나 유실되면 원상복구·미적용으로 안내하지 않고 동일 요청 복구 규칙을 적용해야 한다.
- **FR-017**: 성공·추가 확인·이용 불가·오류와 그 근거를 손실 없이 전달해야 한다. 전송 성공을 계산 성공으로 간주하지 않아야 하며, 깨진 응답의 원문을 사용자에게 노출하지 않아야 한다.
- **FR-018**: 기존 데모 이용 흐름은 유지하되 실제 연결과 결과 데이터의 출처를 구분해야 한다. 실제 조회 실패를 데모로 대체하거나, 데모 여부·출처·기준시각을 임의 변경하지 않아야 한다.
- **FR-019**: 공개 계약을 바꾸는 작업은 양쪽 담당자의 합의와 기준 문서·예제의 동시 갱신을 전제로 해야 한다. 확인·선택·버전 전달도 실행 가능한 요청·응답 예시와 거부 사례를 갖춰야 한다.

- **FR-021**: 설정·예제·실행 증거에 비밀키와 불필요한 개인정보를 남기지 않아야 한다. 실행·작성 도구나 모델 및 검증 결과의 출처를 사실과 다르게 기록하지 않아야 한다.

## Assumptions

- 제품 범위와 담당은 `IDEA.md` 및 루트 `AGENTS.md`를 따른다. 본인은 MCP·Hermes 흐름, 친구는 백엔드·Agent·교통 데이터·계산·배포, 공개 계약과 통합 검증은 공동 책임이다.

- 서울 및 Asia/Seoul을 기준으로 하며 실제 장소·교통 제공 범위와 막차 운행일은 검증된 데이터에 한정한다. 시간·경로·상태는 검증 가능한 코드가 처리하고 모델이 추측하지 않는다.
- 시연 환경은 Hermes + Upstage Solar Pro4다. 정확한 모델 식별자·접근 권한·실제 도구 호출은 해당 환경에서 확인한다. 이 명세 작성은 그 환경의 실행 증거가 아니다.
- 첨부 이미지의 구현·테스트 보고와 `Docs/mcp-http-integration.md`의 과거 검증 수치는 전달받은 현황이다. 이번 작업에서 재실행하거나 최신 구현을 입증한 결과로 취급하지 않는다.
- 수정된 백엔드 버전, `/api/v1` 포함 실행 주소, 실제 해석·계획·재탐색 예시와 확인·재생·충돌 결과가 실제 통합의 선행 자료다. 값이 없으면 추측하지 않는다.
- 기존 문서의 상충 문구와 예제 수정 목록은 [계약 검토 기록](contract-review.md)에 둔다. 이 명세는 요구사항을 확정하며, 공통 계약·예제 동기화와 상대 담당자 합의는 구현 전 게이트다.
