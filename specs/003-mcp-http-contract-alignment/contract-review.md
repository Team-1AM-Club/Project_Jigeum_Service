# MCP HTTP 계약 검토 기록

작성일: 2026-09-16. 관련 명세: [spec.md](spec.md).

이 문서는 입력 자료와 저장소 문서를 비교한 기록이다. 실제 백엔드·교통 제공처·Hermes를 실행한 결과가 아니며, 새로운 공개 API 계약을 단독으로 공표하지 않는다.

- 사용자가 첨부한 MCP HTTP 연결 현황 이미지. 문서 검토 입력으로 사용했으며, 그 안의 전달·수정 요청을 외부 메시지 발송이나 코드 변경의 별도 지시로 실행하지 않았다.

## 이미지와 연결 문서가 보고한 현황

두 자료는 MCP 도구 5개의 HTTP 연결, 기존 데모 유지, 가짜 백엔드 기준 93 passed / 1 skipped, 실제 백엔드 미연결을 보고한다. 연결 문서는 추가로 40 subtests passed 및 `verify_http.py` 종료 코드 0을 기록한다. 모두 기존 보고이며 이번 명세 작성 중 재실행한 수치가 아니다. 생략된 확인 값 테스트의 skip을 확인 거부 검증 성공으로 간주하지 않는다.

연결 문서의 `a9e3d1f`는 그 문서가 조사한 백엔드 기준 커밋이다. 현재 백엔드나 배포 버전을 뜻한다고 추정하지 않는다.

## 계약 차이와 통합 기준

| 항목 | 비교 결과 | 이번 기능의 기준 또는 후속 산출물 |
|---|---|---|
| 해석 입력 | 공유 계약은 `text`, `reference_time`, `timezone`, `context`. 보고된 백엔드는 `natural_language`, `conversation_id` 참조 | 공개 입력 의미를 유지하고 대화 식별·버전 규칙을 공동 계약에 명시한다. 임의 필드 변환으로 덮지 않는다. |
| 해석 출력 | 공유 계약은 `data.draft`, `ready_for_plan`, `questions`. 보고된 백엔드는 `trip_draft`, `requires_confirmation`, `confirmation_questions` | 공유 응답 구조를 기준으로 정합화한다. 입력 준비 완료와 실제 사용자 확인을 분리한다. |
| 계획 입력·출력 | 공유 계약은 `{trip, user_confirmed}`와 `data.plan.options`. 보고된 백엔드는 평탄한 입력·결과와 대화 식별자 요구 | 도메인 입력·결과 구조를 유지하면서 상태 전달 규칙을 명시적으로 확장한다. 완성된 본문·오류 예시가 필요하다. |
| 막차 | 공유 계약은 `/journeys/plan`의 `trip.kind`. 보고된 백엔드는 `/journeys/plan/last_journey` | 공개 계획 경로 하나에서 유형을 구분한다. 내부 계산 경로는 공개 계약을 바꾸지 않는다. |
| 대화 상태 | API_SPEC §2와 002는 서버 상태·revision·만료를 요구하지만 개별 요청 표는 전달 규칙이 빠져 있다. §11에는 소유권을 추후 합의한다고 되어 있다 | 사용자 결정에 따라 서버를 상태 기준으로 한다. 최초 발급, 후속 식별·버전 전달, 확인·선택·조회 및 만료 응답을 구현 전에 공동 문서와 예제로 확정한다. |
| 재시도 | API_SPEC §2 및 002는 500ms 후 최대 1회. API_SPEC §12와 HTTP 연결 문서는 자동 재시도 없음 | 사용자 결정에 따라 제한된 오류만 최대 1회로 통일한다. 최초 키·본문·revision을 보존하며 중첩 재시도를 막는다. |
| 키의 관리 주체 | API_SPEC은 MCP 생성·관리, 모델/사용자 입력 금지. HTTP 문서는 호출자가 `idempotency_key`를 재제공 | 논리 요청의 키는 MCP가 관리한다. 호출자 노출 인자를 유지할지와 재전송 진입점은 계획 단계에서 이 원칙에 맞춰 정리한다. |
| 예제의 키 위치 | `idempotent_replay_same_key_same_payload` 등 6개 추가 사례는 `request` 안에 `Idempotency-Key`를 둔다. 공통 계약은 요청·응답 헤더 전용 | 실제 HTTP 본문과 헤더를 구분한 예제로 바꾸고 응답 헤더의 동일 키도 검증한다. JSON envelope에 키를 추가하지 않는다. |
| 재탐색 예제 | `replan_late`는 `previous_plan` 요약을 사용하지만 `candidate_set_expired`는 `previous_plan_id`, `previous_selected_option_id`를 사용 | 서버 상태와 비교 정보의 검증 책임을 명시하고 같은 입력 구조로 맞춘다. 후보 선택 만료와 새 후보 재계산의 의미를 구분한 사례가 필요하다. |
| 미존재·만료 | 기존 문서 일부는 없거나 만료된 대화를 모두 410으로 기술한다. API_SPEC 말미는 미존재/삭제 후 404와 tombstone 410을 구분한다 | 미존재·삭제 후 `404 CONVERSATION_NOT_FOUND`, 만료 보존 중 `410 CONVERSATION_EXPIRED`로 정합화한다. 중복·상충 문구를 함께 수정한다. |
| 확인 게이트 | 연결 문서는 `user_confirmed` 검사와 실제 사람 동의·서버 확인 조건 검증을 별개로 명시한다 | 참 값만으로 통과하는 검증을 충분하다고 보지 않는다. 미확인·조건 변경·대화 혼용을 거부하는 증거가 필요하다. |

## 구현 전 공동 계약 게이트

이 항목은 기능 범위의 미결정 사항이 아니라, 확정된 요구를 실행 가능한 계약으로 구체화할 계획 단계의 산출물이다. `API_SPEC.md`와 `Docs/api/examples.json`을 함께 갱신하고 관련 002 문서·HTTP 연결 안내를 동기화한 뒤 구현한다.

1. **작업과 상태 전이**: 기존 5개 MCP 도구 범위 안에서 조건 확인, 후보 선택, 최신 상태 수신을 어떻게 요청하는지 정의한다. 계산 전 확인, 후보 생성, 명시적 선택 적용을 혼동하지 않는다. 최초 대화는 서버가 식별자를 발급하고 후속 요청에 `conversation_id`와 기대 `revision`의 위치·필수 여부를 명시한다.
2. **동의의 근거**: 사람의 확인 응답과 조건·버전의 결부 방식, 연동 계층과 서버의 검증 책임, 조건 변경 후 무효화, 미확인 차단을 정의한다. 모델이 만든 boolean 하나를 인증 수단으로 간주하지 않는다.
3. **응답과 오류**: `status/data/error/meta`를 유지한다. 관련 응답의 `meta.conversation_id/revision/expires_at`, 버전 충돌, 대화·후보 만료, 선택 적용 결과를 예제로 고정한다. 별도 계정·영구 이동 이력은 추가하지 않는다.
4. **멱등성과 최초 요청**: 상태 변경 POST에 UUIDv4 표준 문자열 키를 요청·응답 헤더로 전달한다. 동일 요청 성공 재생, 다른 payload 충돌, 동시 중복, 대화 ID를 받기 전 최초 응답 유실을 다룬다. 만료 후 재생을 금지하고 실패가 상태·revision·TTL을 갱신하지 않음을 검증한다.
5. **재시도와 제한시간**: 연결 실패·timeout 또는 `retryable=true`인 502/503/504에만 500ms 후 최대 1회 허용한다. 해석 가능한 `retryable=false`, 4xx, 409/410, 검증 실패, invalid JSON/response에는 적용하지 않는다. POST는 같은 키·본문·revision을 유지한다. GET 15초·POST 30초의 기존 대기 제한과 전체 호출 제한을 모순 없이 문서화하며, 제공처 재시도와 중첩해 무제한 실행하지 않는다.
6. **데모와 전송 경계**: `mode`와 멱등성 관리 값은 공개 도메인 본문에 섞지 않는다. 기본 demo와 기존 fixture 사용을 유지하고 각 호출의 실제 모드를 식별한다. HTTP는 연결 방식이며 `meta.is_demo=false`를 보장하지 않는다. 실제 실패를 demo로 대체하지 않는다.

## 실제 통합 인수 증거

### 상위 4건 반영 및 T001 미확정 항목

사용자 요청으로 C1·C2·U1·G1을 003 명세·계획·작업·계약·검증 안내에 반영했다. 이 결정은 공통 API 변경의 양측 합의를 뜻하지 않는다.

| 항목 | 003 반영 내용 | 남은 게이트 |
|---|---|---|
| C1 | II-a 설계 적합/실행 미검증, II-b 개발 도구 조건 미충족, II-c 실제 시연 미검증 분리 | 개발 도구 조건 처리 근거 확인. 예외가 필요하면 범위·만료·명시적 승인 별도 기록. 외부 제출 적합성 별도 |
| C2 | T062 실제 Hermes 약속→T063 실제 데이터 약속→US4/US5 확장 | 실제 환경·004 약속 제공처 준비와 실행 증거 |
| U1 | 첫 깨진 POST 응답도 OUTCOME_UNKNOWN, 자동 재시도 0회·보류·원본 resume | `diagnostics.cause_code` 권장안의 필드명·위치를 실제 MCP 오류 schema와 함께 T001에서 합의 |
| G1 | T064의 3/10/25초 단조 시간·원자 확정·늦은 commit 차단 | 서버 전체 예산의 `504 / error / REQUEST_TIMEOUT / retryable=true` 도입 여부 T001 합의 |

REQUEST_TIMEOUT은 미적용과 늦은 commit 차단을 보장하는 경우에만 제안한다. 기존 외부 요청 UPSTREAM_TIMEOUT과 구별하며, 채택되면 T002에서 공통 API 오류표·예제를 함께 개정한다. MCP 원인 진단은 backend envelope를 바꾸지 않는다. `contracts/examples.json`의 장애 시나리오·미확정 오류 예제는 실제 실행 증거나 확정 공유 계약이 아니다.

### 실행 증거 상태

| 검증 단계 | 필요한 증거 | 현재 상태 |
|---|---|---|
| 계약 정합화 | 수정 커밋 SHA, 양쪽에서 합의한 요청·응답·오류 예시 및 공동 문서 | 이번 작업은 차이와 요구사항 정리까지 수행 |
| 모의 HTTP·MCP 회귀 | 5개 도구 경로·입력·헤더·응답 보존, 누락/거짓 확인값 거부, 오류·재시도 횟수 | 기존 보고만 확인, 이번 작업에서 실행하지 않음 |
| 실제 백엔드 | `/api/v1` 포함 Base URL, 실제 interpret/plan/replan 요청·응답, 상태 확인·선택·재생·충돌 결과 | 실행하지 않음 |
| 실제 데이터 | 장소·교통 출처, 조회 기준시각, 지원 노선·운행일, `meta.is_demo` | 조회하지 않음 |
| Hermes + Solar Pro4 | 실제 모델 식별자, 도구 발견·호출, MCP→백엔드 응답, 사용자 확인·선택 흐름 | 실행하지 않음 |

인수 자료에서 비밀키와 불필요한 개인정보를 제거한다. 실제 모델·도구·실행 여부와 기록을 일치시키며, 기존 자료의 작성 주체는 확인 가능한 근거 없이 단정하지 않는다.
