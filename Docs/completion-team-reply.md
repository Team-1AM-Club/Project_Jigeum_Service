## 3. 재전송 공동 검증

### revision 포함 POST의 동일 key/body/revision

confirm/plan/replan 각각에 대한 응답 유실 테스트는 **현재 이쪽 테스트 파일에 없으며 미실행**입니다. 기존 interpret 재시도 검사와 trip 필드 덮어쓰기 방지 테스트를 대체 근거로 제출하지 않습니다.

MCP 담당 후속 작업으로 세 도구 각각에 expected_revision을 포함한 합성 요청을 만들고, 첫 응답 유실 이후 두 호출의 키·본문·revision 동일성을 검증하겠습니다. 최신 MCP 파일 변경 여부를 수령 목록으로 먼저 대조해 병렬 수정 충돌을 피하겠습니다.

### HTTP 오류 자동 재시도 금지

현재 `_request`는 HTTP 응답을 수신하면 반환된 429·502·503·504를 재시도하지 않습니다. 코드 확인 사실입니다. 이쪽 집중 테스트에는 409에 대한 검증만 있으므로, 네 상태 각각의 실행 검증을 완료로 보고하지 않습니다. 위 후속 합성 테스트에 포함할 대상입니다.

### 두 번 통신 실패 후 안내와 한계

현재 반환은 `ROUTING_PROVIDER_UNAVAILABLE`, `retryable=true`, 메시지는 “백엔드 응답을 확인하지 못했습니다.”입니다. 서버 미적용을 단정하는 문구는 없지만 **처리 결과가 불확실하다는 설명과 새 키 호출 주의가 응답 자체에 충분히 명시되지는 않습니다.**

현재 별도 도구 호출은 새 멱등 키를 생성하고, pending/resume 저장은 없습니다. 따라서 새 키 호출을 이전 요청의 안전한 복구로 안내할 수 없습니다. 사람에게 보여주는 안내 보완 및 합성 테스트는 MCP 담당 범위로 두되, 새 공개 오류·상태·resume을 자동 도입하지 않겠습니다. 실제 Hermes가 어떤 안내를 하는지는 별도 실행 검증 대상입니다.

### timeout·총 시간

- MCP 코드 기본값: `JIGEUM_API_TIMEOUT=15`, 허용 범위 0 초과 120 이하. 개인 실행 환경의 실제 override는 이번에 조회하지 않았습니다.
- `httpx.request(..., timeout=timeout)`를 각 시도에 적용하고 총 2회까지 시도합니다.
- **전체 경과시간 deadline은 없습니다.** HTTPX의 단계별 timeout은 전체 workflow 상한과 다르므로 “총 30초 보장”이라고 보고할 수 없습니다.
- 최신 백엔드 deadline·provider 예산 설정은 패키지 미수령으로 대조하지 못했습니다. 새 전송 구현과 실제 설정값을 받은 후 예산 변경안을 먼저 공유하겠습니다.

### 진행 중 동일 요청 검증 분담·시점

백엔드 담당의 진행 중/완료 응답 재생·외부 조회 횟수·revision·늦은 상태 반영 검증, MCP 담당의 응답 유실·동일 인수 재전송·사용자 안내 검증이라는 수용된 분담을 유지합니다.

시점은 **패키지 적용 검증 완료 후, 지연 첫 요청을 재현할 백엔드 fixture/기동 방법이 준비되면 공동 실행**으로 제안합니다. 현재 확정 일시는 없습니다. 다중 worker/인스턴스 보장과 진행 중 중복 조회 0회는 미구현·미검증 상태를 유지합니다.
