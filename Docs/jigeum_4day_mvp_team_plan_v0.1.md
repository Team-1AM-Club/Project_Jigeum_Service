# 지금 — 2인·4일 앱 MVP 분업 제안

- 작성일: 2026-09-12
- 기준: 사용자에게 남은 개발 기간은 4일. 현재 작업 폴더에서 확인된 파일은 기획 문서이며, 별도의 기존 앱·서버 코드는 확인하지 못했다.
- 성격: 개발 착수 전 범위와 분업 제안. 기존 PRD를 자동으로 대체하지 않는다.
- 목표: 실제 기기에 설치하고, 배포된 서버로 이동 요청을 처리하며, 입력부터 결과·재확인까지 시연 가능한 앱을 제출한다.

## 1. 기본 분업

편의상 본인은 앱, 친구는 서버·AI·교통 데이터를 담당한다. 실제 숙련도가 반대라면 담당자를 교환하되 책임 경계는 유지한다.

| 담당 | 책임 | 완료 기준 |
|---|---|---|
| 본인: 앱·사용 흐름 | 자연어 입력, 장소·시각 확인, 시간 중심 Home, 경로 상세, 출발·도착 수동 확인, 재탐색 버튼, 로컬 알림, 앱 빌드 | 설치된 앱에서 전체 흐름을 실행할 수 있다. |
| 친구: 서버·AI·데이터 | 요청 구조화, 장소 검색·확정 지원, 교통 데이터 검증, 시간 계산, 경로 조회·재탐색, 서버 배포, 오류 응답 | 실제 API로 일관된 결과와 데이터 기준시각을 반환한다. |
| 공동 | API 계약, 핵심 시나리오 검증, 매일 통합, 제출 문서·영상 | 다른 사람의 기기에서도 배포 서버에 연결해 주요 흐름이 동작한다. |

서로 기존에 만든 Skill의 개수로 구현 업무를 나누지 않는다. 하나의 이동 흐름에 여러 Skill의 책임이 들어가므로 앱과 서버의 계약을 기준으로 협업한다.

## 2. 우선 구현할 5개 기능

고객 조사에 근거한 수치 점수는 없으므로 사용자 가치, 구현 부담, 데이터 위험, PRD 적합성을 정성적으로 비교했다.

| 순위 | 기능 | 선정 이유 | 범위와 위험 |
|---|---|---|---|
| 1 | 자연어 입력 → 이동 조건 확인 | 기존 Skill을 제품 사용 흐름으로 연결하고 잘못된 장소·시간 확정을 막는다. | 사용자 입력에서 부족한 정보만 질문. 자동 Calendar 연동은 제외. |
| 2 | 약속의 목표 도착·권장 출발시각 계산 | Time is Hero를 가장 직접적으로 보여주며 시간 계산은 독립 검증이 가능하다. | 확인된 경로 데이터 사용. 미래 출발·도착 조건 지원 여부를 검증하고 현재 ETA를 미래에도 보장하지 않는다. |
| 3 | 데이터로 검증 가능한 막차 Journey | PRD의 약속·막차 두 축을 유지하는 핵심이다. | 첫날 Go/No-Go 결정. 전체 서울·모든 환승을 무조건 약속하지 않는다. |
| 4 | 시간 중심 결과 화면과 이동 관리 | 사용자가 출발시각을 확인하고 다시 앱을 사용할 이유를 만든다. | 로컬 저장, 출발·도착 수동 확인, 가능하면 권장 출발시각 로컬 알림. |
| 5 | 사용자 요청에 따른 재탐색 | 경로가 깨졌을 때 다음 행동을 제시하는 가치를 보여준다. | 사용자가 현재 위치·시각을 확인하고 버튼으로 요청. 자동 이탈 감지는 제외. |

4일 버전에서 보류할 기능: GPS 상시 추적, 자동 출발·도착 판정, 백그라운드 교통 재계산, 자동 경로 이탈 감지, 자동 Calendar 동기화, 개인화 학습, 전체 서울의 모든 막차·환승 보장, 택시 Hybrid 최적화, 회원가입·계정 동기화.

이는 PRD 전체보다 작은 제출용 범위다. 지원 지역·노선·계산 조건을 앱과 제출 자료에 명시한다.

## 3. 첫날에 결정할 기술·데이터 조건

### 기술 선택

- 이미 익숙한 앱·서버 기술이 있으면 그것을 우선한다.
- 두 사람이 JavaScript/TypeScript에 익숙하고 앱 코드가 없다면 Expo + React Native를 후보로 삼는다.
- 서버는 친구가 가장 익숙한 프레임워크 하나만 사용한다. 새 프레임워크 학습을 일정에 넣지 않는다.
- 앱은 로컬에 이동 기록을 저장하고, 서버는 우선 요청을 처리하는 구조로 작게 시작한다. 계정·영구 서버 상태가 필요한 자동화는 뒤로 미룬다.
- API 키와 모델 호출은 서버에서 처리한다.
- Timely Skill을 외부 앱에서 실행하는 지원 방식과 대회에서 요구하는 Timely/Solar 사용 조건을 첫날 확인한다. 외부 호출 가능성을 확인 없이 전제하지 않는다.

### 교통 데이터 Go/No-Go

첫날 초반 4~6시간 안에 후보 제공처 하나를 우선 검증한다.

1. 사용할 키·권한을 즉시 확보할 수 있는가?
2. 목적지 확정과 대중교통 경로 조회가 실제로 동작하는가?
3. 미래 시각 또는 도착시각 기준 조회를 지원하는가?
4. 막차 운행일·방향·종착역과 환승 연결을 검증할 수 있는가?
5. 이용 조건·호출 한도 내에서 심사 기간 동안 운영할 수 있는가?

가능하면 지원 범위가 명확한 막차 경로부터 구현한다. 일부 노선만 검증된다면 그 범위로 제한한다. 검증 가능한 데이터가 없으면 사용자 제공 시간표를 이용한 연결 계산으로 제한하고 그 사실을 표시하거나, 막차 기능을 보류하는 결정을 팀이 첫날 내린다. 샘플 경로로 연결한 화면은 개발·시연 데이터임을 표시하며 실제 운행 정보로 제출하지 않는다.

## 4. 첫 2시간에 합의할 API 계약

아래 명칭은 설계 예시다. 실제 구현 전에 두 사람이 한 문서에서 확정한다.

| 작업 | 앱 → 서버 | 서버 → 앱 |
|---|---|---|
| 입력 해석 | 사용자 문장, 기준 날짜·시각, 시간대, 기존에 확정한 조건 | 추출된 이동 조건, 미확정 항목, 확인 질문 |
| 계획 계산 | 확정한 장소, Deadline, 도착 여유, 이동 조건 | 경로, 목표 도착시각, 권장 출발시각, 계산 근거, 데이터 출처·기준시각 |
| 재탐색 | 기존 계획, 사용자 확인 현재 위치·시각, 유지할 조건 | 새 경로·시각, 기존 계획과 달라진 점, 불가능/확인 필요 사유 |

공통 상태는 최소 `ok`, `needs_confirmation`, `unavailable`, `error`로 구분한다. 데이터 없음과 서비스 장애를 성공 응답으로 포장하지 않는다. 날짜·시간대가 포함된 시각 형식을 통일하고, LLM은 구조화된 계산 결과를 설명한다.

## 5. 날짜별 분업과 통합 기준

| 날짜 | 본인: 앱 | 친구: 서버·AI·데이터 | 그날 종료 시 확인 |
|---|---|---|---|
| Day 1 | 앱 생성, 입력·확인·결과 화면 최소 구현, 계약된 샘플 응답 연결, 기기 빌드 | 데이터 검증, API 계약 확정, 최소 서버 배포, 입력 해석과 경로 조회 연결 | 설치한 앱에서 배포 서버 호출. 막차 지원 범위 결정. |
| Day 2 | 실제 응답 연결, 시간 중심 Home, 경로 상세, 로컬 저장·수동 상태 버튼, 가능하면 로컬 알림 | 약속 시간 계산 완성, 선택한 범위의 막차 계산, 확인 필요·데이터 없음·오류 처리 | 자연어 → 확인 → 실제 데이터 기반 출발시각이 기기에서 끝까지 동작. |
| Day 3 | 재탐색 화면·변경 비교, 로딩·오류 화면, 접근 가능한 버튼·문구 정리 | 재탐색, 막차 연결 검증 보완, 시간 경계 테스트, 서버 안정화 | 약속·막차·재탐색 핵심 시연. 저녁부터 기능 추가 중단. |
| Day 4 | 최종 설치 파일, 새 기기 설치, 데모 녹화, 화면 문제 수정 | 배포 환경·API 키·한도·로그 점검, 치명적 결함 수정, 제출 기술 설명 | 설치 파일/링크, 동작하는 서버, 데모 영상, 설명·제약 문서 확보 후 제출. |

첫날의 실기기 빌드가 실패하면 다른 기능 개발과 동시에 해결한다. 마지막 날 처음 빌드하지 않는다. 매일 최소 두 번 앱과 서버를 통합하고, 새 API 형식은 앱 담당자와 합의한 뒤 바꾼다.

## 6. 기존 Skill 재사용

| 처리 | 이번 앱에서의 적용 |
|---|---|
| `resolve-trip-details` | 자연어 구조화·모호한 장소/시간 확인 지침 재사용 |
| `leave-by` · `maginot-line` | 사용자 응답 형식·정책 재사용. 시간 계산과 경로 검증은 코드로 구현 |
| `plan-b-recovery` | 재탐색 후 선택지 비교·설명에 재사용 |
| `departure-alert` | 알림 기준을 명시적 규칙으로 적용. 단순 로컬 알림과 교통 변화 감지는 구분 |
| 나머지 Skill | 필요한 규칙만 가져오고, 12개를 각각의 서비스로 연결하는 구현은 보류 |

현재 Timely 테스트는 일부 대표 입력에서의 동작 확인이다. 실제 앱의 데이터 연결, API 호출, 상태 저장, 알림 실행이 이미 검증됐다는 의미는 아니다.

## 7. 제출 전 필요한 검증

- 새로 설치한 실제 기기에서 배포 서버로 전체 흐름을 실행한다.
- 모호한 목적지·오전/오후는 확인하고, 명확한 19:00 도착 Deadline은 재질문하지 않는다.
- 도착 여유와 도보·환승 여유를 중복으로 빼지 않는다.
- 자정 이후 시각과 날짜 경계를 계산한다.
- 막차 결과는 운행일·방향·환승 연결과 데이터 기준시각을 설명할 수 있어야 한다.
- 경로가 없거나 API가 실패하면 이해할 수 있는 안내와 재시도 동작을 제공한다.
- 알림을 넣었다면 실제 기기에서 권한 거부·수정된 일정의 기존 알림 취소·재예약을 확인한다.
- 샘플 기반 예외 시연은 재현용 시나리오라고 표시한다.

## 8. 배포 방식

제출 규정이 설치 파일 배포를 허용한다면 Android APK를 우선 확보한다. Expo EAS의 internal distribution은 Android APK를 만들고 설치 링크를 공유할 수 있다. iOS ad hoc 배포는 기기 등록과 provisioning 조건이 있으므로 iOS가 필수라면 첫날부터 배포 경로를 확인한다. 앱스토어 공개와 설치 가능한 앱 제출을 구분하고 대회의 실제 요구 형식을 따른다.
